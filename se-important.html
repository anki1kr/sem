Q1. What is software crisis? Discuss its symptoms, causes and how software engineering solves it.

Unit I · 8 marks · Examiner wants the definition, both lists (symptoms, causes) and the link "SE is the cure" — not just one list.

Definition: Software crisis is the set of problems faced in developing software: projects running over budget, behind schedule, of poor quality, hard to maintain and not meeting user requirements. The term became widely used around the 1968 NATO Software Engineering Conference, where the name "software engineering" was also promoted.
  • Symptoms: over budget, late delivery, poor quality/unreliable, hard to maintain, requirement mismatch, project cancelled; also hardware cost falling while software cost rising as a share of total system cost.
  • Causes: growing size and complexity of software; no systematic process (ad-hoc "code and fix"); poor requirement gathering and changing requirements; poor estimation of effort/cost/time and weak project management; little testing and documentation; shortage of trained people.
  • Solution — software engineering: defined process models, requirement analysis (SRS), design methods, testing, software quality assurance, project management, and CASE tools.
  • Recall IEEE: SE is the application of a systematic, disciplined, quantifiable approach to develop, operate and maintain software.
Example
A college orders an admission portal "in 2 months". No written requirements; coding starts on day 1.
Fee rules change midway, the team patches code, testing is skipped, and the portal crashes on result day.
Late + over budget + poor quality + requirement mismatch = software crisis in miniature.
Mnemonic Symptoms "BLQMR": over Budget, Late, poor Quality, hard to Maintain, Requirement mismatch.
If it comes as 4 marks: write the definition, draw Fig 1.3 (symptoms) with a one-line explanation each, and give any 3 causes with the one-line "solution = software engineering" conclusion.
Quick recall Crisis = late, costly, buggy, unmaintainable software. Cause = no discipline. Cure = software engineering.

Q2. Explain the characteristics of software. How is it different from hardware? Draw the failure curves.

Unit I · 8 marks · Examiner wants the failure-curve diagram AND the hardware-vs-software table; this is Unit I's most diagram-dependent question.

Definition: Software characteristics are the properties that distinguish software from physical (hardware) products and decide how it must be developed and maintained.
  • Developed or engineered, not manufactured: cost is in engineering, not production; copying software costs almost nothing.
  • Does not wear out: no physical wear, so the idealized curve falls and stays flat — but software deteriorates because every change (maintenance) can add new defects, so the actual curve shows spikes and its minimum slowly rises.
  • Custom built: most software is still built for a specific need, though the industry is moving towards component reuse.
  • No spare parts: a software failure means a design/coding error, not a part to replace — maintenance is more complex.
  • Flexible: easy to change, which also makes it easy to change badly.

ProductionManufacturedDeveloped / engineered
WearWears out with timeDoes not wear out, but deteriorates due to changes
Failure curveBathtub curveIdealized flat curve; actual curve with spikes
RepairReplace spare partFix the design/code, no spare parts
Copy costHigh (material, labour)Almost zero
Example
A UPI app works fine for months. An update adds a new feature and accidentally breaks bill payment.
Nothing physically wore out; the failure came from a change — a spike on the actual curve.
Mnemonic E-W-C: Engineered (not manufactured), does not Wear out, Custom built (moving to component reuse).
If it comes as 4 marks: draw Fig 1.2 and explain only "does not wear out but deteriorates" plus "engineered, not manufactured" and "custom built" — skip the full table, keep 2-3 rows.
Quick recall Hardware wears out (bathtub). Software does not wear out but deteriorates, because every change can add defects.

Q3. What is a software process? Explain the generic process framework, and the characteristics of a good software process and a good software product.

Unit I · 8 marks · Splits cleanly into 4+4: (a) process framework, (b) good process/product characteristics.

Definition: A software process is a set of activities, actions and tasks, with their associated results, carried out to develop and maintain a software product. A good process is judged by whether it makes good software likely; a good product is judged by how well it runs, moves and changes.
  • (a) Five framework activities: Communication (gather requirements) → Planning (estimate cost, schedule, risk) → Modeling (analysis + design models) → Construction (code + test) → Deployment (deliver, get feedback, support).
  • Umbrella activities run through the whole project: tracking & control, risk management, SQA, technical reviews, measurement, configuration management, reusability management, work product preparation.
  • (b) Good process (Sommerville, 8 points): understandability, visibility, supportability, acceptability, reliability, robustness, maintainability, rapidity.
  • Good product (McCall's three views): operational (correctness, efficiency, usability, reliability, security), transition (portability, reusability, interoperability), maintenance (maintainability, flexibility, modularity, scalability).
BasisGood process characteristicsGood product characteristics
Applies toThe way software is builtThe software delivered
Judged byDevelopment team, managementUsers and maintainers
ExamplesVisibility, rapidity, robustnessCorrectness, portability, maintainability
Mnemonic Process: "U-V-S-A R-R-M-R" (Understand, View, Support, Accept, Rely, Robust, Maintain, Rapid). Product: O-T-M (Operational, Transition, Maintenance).
If it comes as 4 marks: answer only ONE half — either (a) Fig 1.5 + the five framework activities + umbrella activities, or (b) Fig 1.7 or 1.8 + the 8/3 characteristics list.
Quick recall Process: Communication, Planning, Modeling, Construction, Deployment + umbrella activities. Good process: 8 Sommerville points. Good product: Operational, Transition, Maintenance.

Q4. Explain the waterfall model with a neat diagram. How does the iterative waterfall model improve it? Give advantages, disadvantages and applicability.

Unit I · 8 marks · The single most likely 8-mark question in this unit — examiner wants the staircase diagram drawn correctly with feedback arrows.

Definition: The waterfall model (classical life cycle / linear sequential model), usually attributed to W. W. Royce (1970), develops software sequentially through phases, each phase starting only after the previous one is complete and its output document is approved.
  • Phases: requirement analysis & specification (output SRS) → design (output SDD) → implementation & unit testing → integration & system testing → operation & maintenance.
  • Classical waterfall: strictly one-way; assumes no mistakes are ever found in earlier phases — idealistic.
  • Iterative waterfall: adds feedback paths from every phase to the previous one, so an error found later is corrected where it was introduced. No feedback to the feasibility study.
  • Document-driven: each phase ends with a document that is reviewed and signed off.
AdvantagesDisadvantages
Simple, easy to understand and explainRequirements must be fully known at the start
Clear milestones and documents; easy to manageWorking software appears only late
Each phase reviewed before the next beginsChanges are costly once a phase is frozen
Good documentation for maintenancePoor risk handling; errors found late are expensive

When to use: requirements clear, complete and stable; technology well known; short project, e.g. converting a fixed paper form into a small payroll system.

Mnemonic Phases "R-D-I-I-O": Requirements, Design, Implementation, Integration, Operation.
If it comes as 4 marks: definition + Fig 1.11 (classical part only, solid arrows) + 3 advantages + 3 disadvantages; mention the iterative feedback in one line only.
Quick recall Waterfall = sequential phases, document at each end, needs fixed requirements. Iterative waterfall = same + feedback paths.

Q5. Explain the prototype model with a diagram. Differentiate throwaway and evolutionary prototyping.

Unit I · 8 marks · Examiner wants the refine-loop flowchart drawn correctly and the throwaway-vs-evolutionary table.

Definition: The prototyping model builds a working prototype (a partial, quick, low-cost version with limited functionality), gets customer evaluation, refines it repeatedly until requirements are clear, then engineers the actual product.
  • Requirements gathering: overall objectives and known needs are defined.
  • Quick design: focuses on what the user sees (screens, input/output formats).
  • Build prototype: quick and dirty; efficiency and error handling are ignored.
  • Customer evaluation & refine: loop until customer is satisfied.
  • Engineer product: final SRS written, then the real system is designed, coded and tested properly.
BasisThrowaway (rapid) prototypingEvolutionary prototyping
Fate of prototypeDiscarded after requirements are clearRefined step by step into the final system
PurposeClarify requirementsDeliver a working system gradually
Code qualityQuick, low quality is acceptableMust be good quality from the start
Best forPoorly understood requirementsWell-understood parts built first, rest evolves
Example
A canteen wants a pre-order app but cannot describe the screens.
Team builds clickable menu and cart screens in a week; students try it and ask for "UPI option" and "pickup time slot".
Prototype fixed the requirements before real coding started.
Mnemonic "G-Q-B-E-R-E": Gather, Quick design, Build, Evaluate, Refine, Engineer.
If it comes as 4 marks: definition + Fig 1.12 (steps only, skip the loop detail) + throwaway-vs-evolutionary in 2 rows.
Quick recall Prototype = quick sample, customer feedback loop, then build properly. Use when requirements are unclear.

Q6. Explain the incremental model and evolutionary development. Then explain the spiral model with its four quadrants and say why it is a meta-model.

Unit I · 8 marks · Splits cleanly into 4+4: (a) incremental/evolutionary, (b) spiral — covers the remaining Unit I model types in one answer.

Definition (Incremental model): Delivers software in a series of increments; each passes through analysis, design, coding and testing, and adds new functionality to the previous release. The first increment is the core product.
  • (a) Incremental: requirements broadly known and prioritised; each increment is a mini waterfall; pros — working software early, risk spread over releases; cons — needs good up-front design so increments fit together.
  • Evolutionary development: an initial version is built from an outline description, refined through many versions until adequate; specification, development and validation happen concurrently; used when requirements are unclear and evolving.
  • (b) Spiral model (Boehm) is risk-driven, combining prototyping's iteration with waterfall's discipline. Four quadrants per loop: 1 determine objectives, alternatives, constraints; 2 evaluate alternatives, identify and resolve risks; 3 develop and verify the next-level product; 4 plan the next iteration.
  • Meta-model: one low-risk loop looks like waterfall; prototypes in quadrant 2 give prototyping; repeated loops give evolutionary development — so the spiral contains the other models.
BasisIncremental modelEvolutionary development
RequirementsMostly known at start, divided into incrementsNot fully known; discovered through versions
Each cycle deliversA new set of planned featuresAn improved version of the whole system
DocumentationDocumented per incrementOften weak; low visibility
Mnemonic Incremental = Add (new room each release); Evolutionary = Grow (plant keeps changing shape). Spiral quadrants "O-R-D-P": Objectives, Risk analysis, Develop, Plan.
If it comes as 4 marks: answer only ONE half — either (a) Fig 1.13 + core-product idea + incremental/evolutionary table, or (b) Fig 1.15 + the four quadrants + why meta-model.
Quick recall Incremental: core first, planned releases. Evolutionary: outline → versions refined by feedback. Spiral: risk-driven loops of 4 quadrants, a meta-model.

Q7. Explain the types of software requirements and the requirement engineering process.

Unit II · 8 marks · Splits cleanly into 4+4: (a) requirement types, (b) the 5-step RE process — the foundation question for all of Unit II.

Definition: A requirement is a feature of the system or something it must be capable of doing. Requirement engineering is the systematic use of principles, techniques and tools to elicit, analyse, document, review and manage requirements; its output is the SRS.
  • (a) Functional: what the system must DO (SRMS: compute total and grade). Non-functional: how well it does it — performance, security, usability (SRMS: result of 2,000 students in 10 seconds). Domain: rules from the application area (a student below pass mark is FAIL).
  • Known / Unknown / Undreamt: known = stakeholder states it; unknown = forgotten; undreamt = stakeholder cannot imagine it due to limited domain knowledge.
  • (b) Elicitation: gather from stakeholders (interviews, FAST, QFD, use cases). Analysis: remove conflicts/gaps and model them — concretely: draw the context diagram → optional prototype → model with DFD/data dictionary/ER → finalise with the customer. Documentation: write the SRS. Review: check correctness, completeness, consistency before sign-off. Management: control changes throughout, keep traceability.
BasisFunctional requirementNon-functional requirement
MeaningWhat the system doesHow well the system does it
TestFunctional (black-box) testingPerformance, load, security testing
SRMS exampleGenerate marksheet for a roll numberMarksheet page opens in under 3 seconds
Mnemonic "Every Artist Draws, Reviews, Manages" = Elicitation, Analysis, Documentation, Review, Management. Types: K-U-U = Known (said), Unknown (forgot), Undreamt (never imagined).
If it comes as 4 marks: answer only ONE half — either (a) Fig 2.1 + functional/non-functional/domain with examples, or (b) Fig 2.3 + the 5 process steps in one line each.
Quick recall Functional = what, Non-functional = how well, Domain = from the field. RE: Elicit, Analyse, Document, Review (+ Manage) → SRS.

Q8. Explain FAST and QFD as requirement elicitation techniques.

Unit II · 8 marks · Splits cleanly into 4+4: (a) FAST, (b) QFD — the two named techniques the syllabus calls out explicitly.

Other elicitation techniques exist — interviews (structured / unstructured) and brainstorming (facilitator, no criticism, record and prioritise all ideas) — but FAST and QFD are the two the examiner names.

Definition (FAST): A team-oriented technique in which customers and developers work together in a facilitated meeting to identify the problem, propose solutions and specify preliminary requirements.
  • (a) FAST is held at a neutral site, run by a facilitator, with a fixed agenda; every attendee brings four lists — Objects, Services, Constraints, Performance (OSCP); lists are combined into a consensus list, sub-teams write mini-specifications, unresolved points go to an issues list, and one sub-team writes the draft specification.
Definition (QFD): A quality management technique that translates the voice of the customer into technical requirements, with emphasis on maximising customer satisfaction (originated in Japanese manufacturing).
  • (b) QFD finds three types of requirement: Normal (stated explicitly, e.g. print marksheet), Expected (so basic nobody states them, e.g. totals always correct — absent = very dissatisfied), Exciting (beyond expectations, e.g. SMS alert on result — present = delighted).
  • Steps: identify stakeholders → list requirements → rate importance 1 to 5 → translate high-value ones into technical requirements, classify as achievable / deferred / dropped.
Mnemonic FAST lists "OSCP". QFD types "No Extra Excitement": Normal, Expected, Exciting.
If it comes as 4 marks: answer only ONE half — either (a) Fig 2.5 + neutral site/facilitator/agenda + OSCP lists, or (b) Fig 2.7 + normal/expected/exciting + the 4 QFD steps.
Quick recall FAST: neutral site + facilitator + OSCP lists → consensus → mini-specs → draft spec. QFD: customer voice → technical requirements; Normal/Expected/Exciting; House of Quality = WHATs vs HOWs.

Q9. What is a DFD? Explain its symbols, rules and levels. Draw the context diagram (level 0) for a Student Result Management System.

Unit II · 8 marks · Diagram-heavy: examiner wants the 4 symbols drawn correctly AND a valid context diagram with no direct entity-to-store flow.

Definition: A Data Flow Diagram (DFD), also called a bubble chart, is a graphical representation of the flow of data through a system, showing external entities, processes, data stores and data flows. It shows data, not control.
  • Symbols: circle = process (verb phrase + number), rectangle = external entity (noun), parallel lines = data store, arrow = named data flow.
  • Rules: every process needs at least one input and one output (no black hole/miracle); data cannot flow directly entity→entity, entity→store or store→store — a process must be in between; a DFD shows no loops/decisions/sequence; balancing — a parent's inputs/outputs must equal its child diagram's net inputs/outputs.
  • Levels: Level 0 = context diagram, the whole system as one process with all external entities, no stores; Level 1 = the bubble exploded into 3-7 main processes with data stores; Level 2 = one Level-1 process exploded further (leveling: 3.0 → 3.1, 3.2, 3.3).
BasisDFDFlowchart
ShowsFlow of dataFlow of control (steps)
Decisions / loopsNot shownShown (diamond, loop back)
LevelsHierarchical (0, 1, 2)Usually a single level
Mnemonic "PEDS": Process (circle), Entity (rectangle), Data store (parallel lines), Signal of data = flow (arrow).
If it comes as 4 marks: definition + Fig 2.10 (symbols) + any 3 rules; or Fig 2.11 (context diagram) + level 0/1/2 in one line each.
Quick recall 4 symbols. Level 0 = one bubble, no stores. No entity-to-store direct flow. Balance parent and child. No control flow.

Q10. What is a data dictionary? Explain its notation and write entries for a DFD.

Unit II · 8 marks · Examiner wants the notation table AND at least 2-3 worked entries, not just the definition.

Definition: A data dictionary is a repository containing descriptions of every data flow, data store and data element in the DFD, together with their composition, aliases and usage — giving one precise meaning to every name.
  • Purpose: analysts, designers, programmers and testers use the same term with the same meaning; removes ambiguity and duplicate names (aliases).
  • An entry contains: name, aliases, where/how used (input, output, store), content description (in the notation), supplementary information (type, range, default).

Q11. Explain ER diagrams: entities, attribute types, relationships, cardinality and participation. Draw an ER diagram for a result system.

Unit II · 8 marks · Diagram-heavy: examiner wants the symbol set drawn AND the actual ER diagram with correct cardinality labels.

Definition: An Entity-Relationship (ER) diagram, proposed by Peter Chen (1976), represents the entities of a system, their attributes and the relationships among entities.
  • Entity: real-world object with independent existence (Student). Weak entity: cannot be uniquely identified by its own attributes, depends on an owner entity; double rectangle.
  • Key attribute uniquely identifies (underlined); composite splits into sub-parts (Name = First + Last); multivalued can hold many values (double ellipse); derived is computed from another attribute (dashed ellipse).
  • Relationship: association among entities (diamond), may carry its own attribute. Degree: unary/binary/ternary. Cardinality: 1:1, 1:N, M:N. Participation: total (double line, every entity must participate) or partial (single line).
BasisDFDER diagram
ModelsProcesses and flow of dataStructure of data and relationships
Leads toModule / function designDatabase (table) design
Common mistake: Putting Marks on STUDENT. A student has different marks per subject, so Marks hangs on the Takes relationship, not on either entity.
If it comes as 4 marks: Fig 2.15 (symbols) + entity/weak entity + 2 attribute types; or Fig 2.17 (ER diagram) + cardinality (M:N, 1:N) only.
Quick recall Rectangle entity, diamond relationship, ellipse attribute (underline key, double = multivalued, dashed = derived). Cardinality 1:1, 1:N, M:N. Double line = total participation.

Q12. What is an SRS? Explain the characteristics of a good SRS (IEEE 830) and its organization.

Unit II · 8 marks · Splits cleanly into 4+4: (a) nature + 8 characteristics, (b) IEEE 830 organization — a near-certain question.

Definition: A Software Requirements Specification (SRS) is a document that completely describes WHAT the proposed software should do, without describing HOW — the contract between customer and developer.
  • (a) Nature (5 issues, FEPAD): Functionality, External interfaces, Performance, Attributes (portability, security), Design constraints. Must NOT include design details or project details (cost, schedule, staffing).
Poor requirementViolatesImproved
"The system should be fast."Unambiguous, Verifiable"Marksheet generated in 3 s for 95% of requests."
Requirement with no id or sourceTraceable"FR-3 (source: Exam Cell interview)"
  • (b) IEEE 830 organises an SRS into three sections: 1 Introduction (purpose, scope, definitions, references, overview), 2 Overall description (product perspective, functions, user characteristics, constraints, assumptions — background only, not detailed requirements), 3 Specific requirements (external interfaces, functions as FR-1/FR-2, performance, logical database, design constraints, system attributes — detailed enough to design and test), plus appendices and index.
Mnemonic "Cute Unicorns Can Carry Red Velvet Muffins Tonight" = Correct, Unambiguous, Complete, Consistent, Ranked, Verifiable, Modifiable, Traceable.
If it comes as 4 marks: answer only ONE half — either (a) definition + FEPAD in one line + Fig 2.19 (8 characteristics), or (b) Fig 2.20 + the three section names with 2 sub-points each.
Quick recall SRS = WHAT not HOW. Nature: F-E-P-A-D. Characteristics: C-U-C-C-R-V-M-T. Organization: 1 Introduction, 2 Overall description, 3 Specific requirements.

1-mark questions

Q1. Define software engineering (IEEE).
The application of a systematic, disciplined, quantifiable approach to the development, operation and maintenance of software.
Q2. What is the formula for software?
Software = Programs + Documentation + Operating procedures.
Q3. Define software crisis.
Software projects running over budget, late, of poor quality, unmaintainable and not meeting requirements.
Q4. List two causes of software crisis.
Growing size and complexity of software; absence of a systematic process (ad-hoc code-and-fix).
Q5. Define software process.
A set of activities, actions and tasks carried out to develop and maintain software: Communication, Planning, Modeling, Construction, Deployment.
Q6. What are umbrella activities?
Activities run throughout the process: project tracking, risk management, SQA, technical reviews, measurement, configuration management.
Q7. What is SDLC?
The period from conception of software to its retirement, through feasibility, requirements, design, coding, testing and maintenance.
Q8. Differentiate classical and iterative waterfall.
Classical is strictly sequential with no going back. Iterative adds feedback paths to correct errors in the phase where they occurred.
Q9. Define the prototype model.
A quick, partial, low-cost working version of a system, built to confirm customer requirements before the real product is engineered.
Q10. Throwaway vs evolutionary prototyping.
Throwaway is discarded once requirements are clear; evolutionary is refined step by step into the final system.
Q11. Name the four quadrants of the spiral model.
Determine objectives/alternatives/constraints; evaluate alternatives and resolve risks; develop and verify next-level product; plan next iteration.
Q12. What is an increment?
A deliverable part of software adding new functionality to earlier releases; the first increment is the core product.
Q13. Define requirement engineering.
Systematic use of principles, techniques and tools to elicit, analyse, document, review and manage requirements; output is the SRS.
Q14. Differentiate functional and non-functional requirements.
Functional = what the system does; non-functional = how well it does it (performance, security, usability).
Q15. What are known, unknown and undreamt requirements?
Known: stated by the stakeholder. Unknown: forgotten. Undreamt: cannot be imagined due to limited domain knowledge.
Q16. Expand FAST and QFD.
FAST: Facilitated Application Specification Technique. QFD: Quality Function Deployment.
Q17. List the lists prepared in a FAST meeting.
Objects, Services, Constraints, Performance criteria (OSCP).
Q18. What are normal, expected and exciting requirements?
Normal: explicitly stated. Expected: so basic customers do not state them. Exciting: beyond expectations, delight when present.
Q19. Name the symbols of a DFD.
Process = circle, external entity = rectangle, data store = two parallel lines, data flow = named arrow.
Q20. What is a context diagram?
Level 0 DFD showing the entire system as one process with all external entities and data flows.
Q21. What is balancing in a DFD?
Data flows entering/leaving a parent process must match the net inputs/outputs of its child diagram.
Q22. Define data dictionary.
A repository of definitions of every data flow, data store and data item of the DFD, with composition, aliases and usage.
Q23. What do { } and ( ) mean in a data dictionary?
{ } = iteration (repeated); ( ) = optional (may be present or absent).
Q24. Define cardinality in an ER diagram.
The maximum number of entity instances on one side that can relate to one instance on the other side: 1:1, 1:N or M:N.
Q25. Name the three main sections of an IEEE 830 SRS.
1 Introduction, 2 Overall description, 3 Specific requirements (plus appendices and index).
