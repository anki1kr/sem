Unit IISoftware Requirements Analysis & Specifications

How we find out WHAT the customer wants, model it (DFD, data dictionary, ER) and write it down as an SRS. One running example throughout: a Student Result Management System (SRMS).

2.1 Requirements and their types

A requirement is one thing the software must do, or one condition it must satisfy. (software se kya chahiye, uski list)

Definition: A requirement is a feature of the system or a description of something the system is capable of doing in order to fulfil the system's purpose. IEEE 610.12 defines it as a condition or capability needed by a user to solve a problem or achieve an objective.
  • Functional requirements: what the system must DO: inputs, processing, outputs. SRMS example: "The system shall compute the total and grade of each student." (kaam kya karega)
  • Non-functional requirements: HOW WELL it does it: performance, reliability, security, usability, portability. SRMS: "Result of 2,000 students shall be computed within 10 seconds." (kitna achha karega)
  • Domain requirements: come from the application area, not from any one user. SRMS: "A student scoring below the university pass mark in a subject is declared FAIL in that subject."
  • Non-functional sub-types (Sommerville): product (speed, reliability), organisational (standards, process), external (legal, ethical, interoperability).
  • Stakeholder: anyone who is affected by or has a say in the system: customer, end users, developers, testers, managers. SRMS stakeholders: students, teachers, exam cell, college management.

MeaningWhat the system doesHow well the system does it (quality)
DescribesServices, inputs, outputs, behaviourPerformance, security, reliability, usability
TestFunctional (black-box) testingPerformance, load, security testing
If missingA feature is absentSystem works but is slow / unsafe / unusable
SRMS exampleGenerate marksheet for a roll numberMarksheet page opens in under 3 seconds
Mnemonic K-U-U: Known = said, Unknown = forgot, Undreamt = never imagined.
Common mistake: "The system shall be secure" is NOT a functional requirement just because it says "shall". Security is a quality, so it is non-functional.
Quick recall Functional = what, Non-functional = how well, Domain = from the field. Known / Unknown / Undreamt.

2.2 Requirement engineering process

Requirement engineering is the disciplined way of turning a customer's vague idea into a signed, checked document. (idea se SRS tak ka safar)

Definition: Requirement engineering is the systematic use of proven principles, techniques and tools to elicit, analyse, document, review and manage the requirements of a software system. Its output is the Software Requirements Specification (SRS).
  • Requirements elicitation: gathering requirements from stakeholders by interviews, brainstorming, FAST, QFD, use cases. (nikalwana / collect karna)
  • Requirements analysis: studying the gathered requirements, removing conflicts and gaps, and modelling them (context diagram, DFD, data dictionary, ER diagram, prototype).
  • Requirements documentation: writing the final requirements in a standard form: the SRS.
  • Requirements review (validation): customer and developers check the SRS for correctness, completeness and consistency before it is signed. (sahi likha hai ya nahi)
  • Requirements management: controlling changes to requirements during the project, keeping them traceable to design, code and tests.
  • Why it matters: an error in requirements found late costs far more to fix than the same error found early, so effort spent here saves rework.
Common mistake: Some books (Sommerville) list "feasibility study, elicitation and analysis, specification, validation". Same idea, different names; write the Aggarwal & Singh four steps plus management for this syllabus.
Mnemonic "Every Artist Draws, Reviews, Manages" = Elicitation, Analysis, Documentation, Review, Management.
Quick recall Elicit, Analyse, Document, Review (+ Manage) → SRS.

2.3 Requirement elicitation: interviews and brainstorming

Elicitation means drawing requirements out of people's heads. (logon se pooch-pooch ke requirements nikalna)

Definition: Requirement elicitation is the activity of discovering the requirements of a system by communicating with customers, users and other stakeholders. It is also called requirements gathering or requirements capture.

Interviews

  • Most common technique; analyst talks to stakeholders one-to-one or in small groups.
  • Unstructured (open-ended) interview: no pre-set agenda; free discussion to understand the problem. Good at the start. (khuli baat-cheet)
  • Structured interview: a prepared agenda of fairly open questions; every interviewee answers the same set. Good for comparing views.
  • Groups to interview (Aggarwal & Singh): entry-level personnel, middle-level stakeholders, managers, and the users of the software (most important, they use it daily).
  • Limitations: interviewee may not know what to ask for; takes time; answers depend on the interviewer's skill.

Brainstorming

  • Brainstorming: a group technique to generate many new ideas quickly and share them freely.
  • A facilitator leads, handles group bias and conflicts; one person records every idea where all can see it.
  • Rule: no criticism during the session; even wild ideas are written down. (koi idea galat nahi)
  • Output: a list of ideas, which is then reviewed and prioritised; duplicate or impossible ideas are removed.
BasisStructured interviewUnstructured interview
AgendaPre-decided questionsNo fixed agenda
Best usedAfter basic understanding existsEarly, to explore the problem
Comparison of answersEasyDifficult
RiskMay miss unexpected pointsMay drift off topic
Example (SRMS)
Interview teacher: "How do you submit internal marks today?" → requirement: bulk upload of marks.
Brainstorm with exam cell: "SMS result alert", "re-evaluation request", "rank list" → prioritised later.
Interviews give depth; brainstorming gives breadth.
Quick recall Interview = structured / unstructured. Brainstorming = facilitator, no criticism, record all, prioritise later.

2.4 FAST (Facilitated Application Specification Technique)

FAST is a well-run joint meeting where customers and developers build the requirement list together. (dono team ek table pe)

Definition: FAST (Facilitated Application Specification Technique) is a team-oriented elicitation approach in which customers and developers work together in a facilitated meeting to identify the problem, propose elements of the solution, negotiate different approaches and specify a preliminary set of requirements.

Guidelines

  • Meeting held at a neutral site; attended by both developers and customers.
  • Rules for preparation and participation are fixed in advance.
  • An agenda is formal enough to cover all important points, informal enough to allow free flow of ideas.
  • A facilitator (customer, developer or an outsider) controls the meeting.
  • A definition mechanism is used: worksheets, flip charts, wall stickers, electronic board or chat room.

The lists every participant brings

ListMeaningSRMS example
ObjectsThings around, produced by, or used by the systemStudent, marks, marksheet, subject
ServicesProcesses / functions acting on objectsRegister student, enter marks, compute result
ConstraintsCost, size, business rulesPass mark rule, runs on college server
Performance criteriaSpeed, accuracyResult of a class in under 10 s, zero calculation error
  • Mini-specification: a short elaboration of one list entry (an object or service) written by a sub-team, then presented to all for additions and deletions.
  • Unresolved points go to an issues list; each attendee also writes validation criteria; one sub-team writes the complete draft specification.
  • Advantage: shared ownership, fewer misunderstandings. Limitation: needs a skilled facilitator and everyone's time together.
Mnemonic "OSCP" lists = Objects, Services, Constraints, Performance criteria.
Common mistake: FAST here is NOT the "Function Analysis System Technique" of value engineering. In software requirements it means Facilitated Application Specification Technique.
Quick recall Neutral site + facilitator + agenda; lists OSCP → consensus → mini-specs → draft spec.

2.5 QFD (Quality Function Deployment)

QFD turns the voice of the customer into technical requirements, ranked by what the customer values most. (customer ki awaaz ko technical bhasha mein)

Definition: Quality Function Deployment (QFD) is a quality management technique that translates the needs of the customer into technical requirements for software, with emphasis on maximising customer satisfaction. It originated in Japanese manufacturing in the 1970s.

Steps of QFD (Aggarwal & Singh)

  1. Identify all stakeholders (customers, users, developers); note initial requirements and constraints.
  2. List requirements from the customer's point of view.
  3. Assign a value of importance to each requirement, e.g. 5 very important, 4 important, 3 nice to have, 2 not important, 1 unrealistic / needs exploration.
  4. Translate high-value customer requirements into technical requirements, and classify the final list: achievable now, deferred (with reason), impossible (dropped).
Example (SRMS importance rating)
Correct grade calculation ........ 5 (expected)
Printable marksheet .............. 5 (normal)
Marks upload by Excel file ........ 4 (normal)
SMS alert when result declared .... 3 (exciting)
Voice-based result enquiry ........ 1 (needs exploration, deferred)
Build the 5s and 4s first; defer or drop the 1s.
Mnemonic "No Extra Excitement": Normal, Expected, Exciting.
Common mistake: Expected requirements are not "less important" because nobody states them. Their absence causes the most dissatisfaction.
Quick recall QFD = customer voice → technical requirements. Normal / Expected / Exciting. Rate importance 1 to 5. House of Quality = WHATs vs HOWs.

2.6 Use case approach and comparison of techniques

A use case tells the story of how a user and the system interact to get one job done. (user system se kya karwata hai, step by step)

Definition: A use case is a structured description of a sequence of interactions between an actor and the system that yields a result of value to that actor. The use case approach (introduced by Ivar Jacobson) captures requirements from the user's point of view.
  • Actor: an external role (person or another system) that interacts with the system; drawn as a stick figure. (role, naam nahi)
  • Use case: one goal the actor achieves; drawn as an ellipse with a verb phrase ("Enter Marks").
  • System boundary: rectangle separating the system from actors.
  • Association: line between actor and use case. Relationships between use cases: <<include>> (always uses another) and <<extend>> (optional extra behaviour).
  • Use case description (template): name, brief description, actors, pre-condition, basic flow of events, alternative flows, post-condition, special requirements.
Example: use case "Enter Marks"
Actor: Teacher. Pre-condition: teacher is logged in.
Basic flow: 1 select subject → 2 system lists roll numbers → 3 teacher types marks → 4 system validates 0 to 100 → 5 marks saved.
Alternative flow: marks out of range → error shown, re-enter.
Post-condition: marks stored for every student of that subject.

2.7 Requirements analysis

Analysis cleans the raw requirement list: removes conflicts, fills gaps and models the system on paper. (kachcha maal ko saaf karna)

Definition: Requirements analysis is the process of studying and refining the elicited requirements to remove inconsistencies, ambiguities and omissions, and representing them with models so that the customer and developer have the same understanding.
  • Draw the context diagram: whole system as one bubble with external entities around it; fixes the system boundary.
  • Develop prototype (optional): a quick working model / screen mock-up so the customer can react to something visible. (demo dikha ke feedback)
  • Model the requirements: graphical models of functions and data: DFD, data dictionary, ER diagram (also state diagrams, decision tables).
  • Finalise the requirements: inconsistencies and ambiguities resolved with the customer; the agreed set goes into the SRS.
  • Typical problems found: conflicting requirements (two users want opposite things), vague words ("fast", "user-friendly"), missing cases (what if a student is absent?).
Quick recall Context diagram → Prototype → Model (DFD, DD, ER) → Finalise.

2.8 Data Flow Diagrams (DFD)

A DFD shows how data enters, moves through, is stored in and leaves a system. It shows data, not control. (data kahan se aaya, kahan gaya)

Definition: A Data Flow Diagram (DFD) is a graphical representation of the flow of data through a system, showing the external entities, processes that transform data, data stores and the data flows between them. It is also called a bubble chart.
SymbolNameMeaningNaming rule
CircleProcessTransforms input data into output dataVerb phrase + number: "3.0 Compute Result"
RectangleExternal entity (source / sink)Person or system outside, sends or receives dataNoun: "Teacher"
Parallel linesData storeData at rest (file, table)Noun + id: "D2 Marks"
ArrowData flowData in motion between componentsNoun: "marks record"

Gane and Sarson notation draws a process as a rounded rectangle; the meaning is the same.

Rules for drawing a DFD

  • Every process must have at least one input and one output (no black hole, no miracle). (kuch aaye bina kuch nahi niklega)
  • Data cannot flow directly entity → entity, entity → store, or store → store; a process must be in between.
  • Every data flow is named (except flows into/out of a store may take the store's name).
  • A DFD shows no control: no loops, no decisions, no sequence. It is not a flowchart.
  • Balancing: inputs and outputs of a parent process must equal the net inputs and outputs of its child diagram.
  • Processes are numbered; child processes of 3.0 are 3.1, 3.2, 3.3 (leveling).

Levels of DFD

  • Level 0 = context diagram: the whole system as ONE process, with all external entities and flows. No data stores.
  • Level 1: the single bubble exploded into main processes (usually 3 to 7), with data stores.
  • Level 2: one level-1 process exploded further. Stop when each process is simple enough to describe in a mini-spec.

2.9 Data dictionary

The data dictionary is the glossary of every data item named in the DFD, written in a precise notation. (DFD ke har naam ka matlab)

Definition: A data dictionary is a repository that contains descriptions of all data objects used or produced by the software, i.e. every data flow, data store and data element in the DFD, together with their composition, aliases and usage.
  • Purpose: gives one precise meaning to every name, so analysts, designers, programmers and testers use the same terms. (sab ek hi bhasha bolein)
  • Removes ambiguity and duplicate names (aliases); helps check DFD consistency and later database design.
  • Typical contents of an entry: name, aliases, where used / how used (input, output, store), content description (in notation), supplementary information (type, range, default).
  • Entries exist for data flows, data stores and elementary data items (the smallest units, e.g. roll_no).
  • Usually maintained with a CASE tool so that it stays consistent with the diagrams.

2.10 Entity-Relationship (ER) diagrams

A DFD models what the system does with data; an ER diagram models what the data itself is and how pieces of data are related. (data ke beech rishte)

Definition: An Entity-Relationship (ER) diagram is a graphical data model, proposed by Peter Chen (1976), that represents the entities of a system, their attributes and the relationships among entities.

Entities and attributes

  • Entity: a real-world object with independent existence about which data is stored (Student, Subject). Entity set = collection of similar entities.
  • Weak entity: cannot be uniquely identified by its own attributes; depends on an owner entity through an identifying relationship (e.g. Dependent of an Employee). Double rectangle.
  • Key attribute: uniquely identifies each entity (Roll_No); underlined.
  • Composite attribute: can be divided into sub-parts (Name = First + Last); sub-ellipses attached to it.
  • Multivalued attribute: can hold many values for one entity (Phone numbers); double ellipse.
  • Derived attribute: computed from another attribute (Age from DOB, Total from marks); dashed ellipse. (store nahi, calculate hota hai)

Relationships

  • Relationship: an association among entities ("Student Takes Subject"); diamond. A relationship may have its own attribute (Marks on Takes).
  • Degree: number of entity sets taking part: unary (1, e.g. Student mentors Student), binary (2, most common), ternary (3).
  • Cardinality: maximum number of entities on one side related to one entity on the other side: 1:1, 1:N, M:N.
  • Participation: total (every entity must participate; double line) or partial (some may not; single line).
  • Reading Fig 2.17: a student takes many subjects and a subject is taken by many students (M:N); Marks belongs to the pair (student, subject), so it is an attribute of the relationship.
  • One teacher teaches many subjects (1:N). The double line shows total participation of SUBJECT: every subject must have a teacher.

ModelsProcesses and flow of dataStructure of data and relationships
Main symbolsCircle, rectangle, parallel lines, arrowRectangle, diamond, ellipse, lines

Common mistake: Putting Marks on STUDENT. A student has different marks in each subject, so Marks must hang on the Takes relationship, not on either entity.
Quick recall Rectangle entity, diamond relationship, ellipse attribute (underline key, double = multivalued, dashed = derived). Cardinality 1:1, 1:N, M:N. Double line = total participation.

2.11 Requirements documentation and nature of SRS

The SRS is the contract between customer and developer: what will be built, written so both sides read it the same way. (dono ke beech likhit agreement)

Definition: A Software Requirements Specification (SRS) is a document that completely describes what the proposed software should do, without describing how it will do it. Requirements documentation is the activity of writing the analysed requirements into this SRS.

Requirements documentation

  • Documentation is the third step of requirement engineering; its output is the SRS, which is then reviewed.
  • Readers of the SRS: customers and users (check it is what they want), developers (design from it), testers (write test cases), managers (estimate cost and schedule), maintainers.
  • Uses of the SRS: basis of agreement, reduces development effort and rework, basis for cost and schedule estimates, baseline for validation and verification, eases enhancement later.

Nature of SRS: what it must address

  • Functionality: what the software is supposed to do. SRMS: compute total and result status.
  • External interfaces: how the software interacts with people, hardware and other software. SRMS: web form for teachers, printer for marksheets.
  • Performance: speed, availability, response time, recovery time. SRMS: 200 teachers online at once.
  • Attributes: portability, correctness, maintainability, security. SRMS: only a teacher can change marks.
  • Design constraints imposed on the implementation: required standards, language, database integrity policy, resource limits, operating environment.

What an SRS should NOT include

  • No design details: module partitioning, algorithms, database table layout. (kya banana hai, kaise nahi)
  • No project requirements: cost, delivery schedule, staffing, reporting procedures, development method, quality assurance plan.
  • No extra constraints beyond what is truly required; it should describe the product, not the project.
Belongs in SRSDoes NOT belong in SRS
"The system shall show PASS/FAIL for each subject.""Use bubble sort to rank students."
"Marksheet shall be generated within 3 seconds.""Project will finish by 30 November."
"The system shall run on the college Linux server.""Team of 4 developers will be hired."

Mnemonic "Five Easy Pieces Are Done": Functionality, External interfaces, Performance, Attributes, Design constraints.
Quick recall SRS = WHAT not HOW. Addresses F-E-P-A-D. Excludes design details and project details (cost, schedule).

2.12 Characteristics of a good SRS

A good SRS is one that every reader interprets the same way and every requirement in it can be checked. (ek hi matlab, har line test ho sake)

Definition: According to IEEE 830, a good SRS should be correct, unambiguous, complete, consistent, ranked for importance and/or stability, verifiable, modifiable and traceable.
  • Correct: every stated requirement is one that the software shall meet; checked against customer needs. Bad: pass mark written as 40 when the university rule says 35 (if the rule is 35).
  • Unambiguous: each requirement has exactly one interpretation. Bad: "result shall be shown quickly". Good: "within 3 seconds".
  • Complete: includes all significant requirements, the response to all valid and invalid inputs, labels for all figures and tables, and definitions of all terms; no "TBD" left.
  • Consistent: no subset of requirements conflicts (e.g. one line says grade scale A to F, another says 10-point CGPA only). (aapas mein takraav nahi)
  • Ranked for importance and/or stability: each requirement tagged essential / conditional / optional, and how likely it is to change.
  • Verifiable: a finite, cost-effective process exists to check the software meets it. "User friendly" is not verifiable.
  • Modifiable: structure (contents, index, cross-references) lets changes be made easily and consistently; each requirement stated only once.
  • Traceable: backward traceability (to its source: a stakeholder, use case) and forward traceability (to design, code, test) via unique ids like FR-3.

Mnemonic "Cute Unicorns Can Carry Red Velvet Muffins Tonight" = Correct, Unambiguous, Complete, Consistent, Ranked, Verifiable, Modifiable, Traceable.
Common mistake: "Understandable by customer" is often written as a characteristic. It is a desirable quality mentioned in some books, but the IEEE 830 list has exactly the eight above.
Quick recall C-U-C-C-R-V-M-T. Verifiable = testable with numbers; Traceable = backward to source, forward to design/test.

2.13 Organization of SRS (IEEE 830 outline)

IEEE 830 gives a standard table of contents so every SRS is arranged the same way. (SRS ka standard dhaancha)

Definition: IEEE Std 830-1998 (Recommended Practice for Software Requirements Specifications) organises an SRS into three main sections: Introduction, Overall description and Specific requirements, followed by appendices and an index.

1 Introduction

  • Purpose: why this SRS exists and who its intended readers are.
  • Scope: name of the product, what it will and will not do, benefits and goals. SRMS: "computes and publishes semester results; does not handle fee payment".
  • Definitions, acronyms, abbreviations: SRMS, CGPA, DFD.
  • References: documents referred to (university ordinance, IEEE 830).
  • Overview: what the rest of the SRS contains and how it is organised.

2 Overall description (background, not detailed requirements)

  • Product perspective: relation to other systems; system, user, hardware, software and communication interfaces; memory constraints; operations; site adaptation.
  • Product functions: summary of major functions (register, enter marks, compute, report).
  • User characteristics: education, experience, technical skill of users (teachers with basic computer skills).
  • Constraints: regulatory policies, hardware limits, interfaces to other applications, security, reliability needs.
  • Assumptions and dependencies: factors that, if changed, change the requirements (college server available during result week).
  • IEEE 830-1998 also has 2.6 Apportioning of requirements: requirements delayed to future versions.

3 Specific requirements (the main body, detailed enough to design and test)

  • External interfaces: every input and output: name, purpose, source/destination, range, format.
  • Functions: fundamental actions on inputs to produce outputs (validity checks, sequence, error handling). Often written as FR-1, FR-2 ...
  • Performance requirements: static (number of users, terminals, data size) and dynamic (transactions per second, response time).
  • Logical database requirements: types of data, access frequency, integrity constraints, retention.
  • Design constraints: standards compliance (report format, audit trail), hardware limitations.
  • Software system attributes: reliability, availability, security, maintainability, portability.
  • The specific requirements can be organised by mode, user class, objects, feature, stimulus or functional hierarchy.
Mnemonic Section 1 "PSDRO" = Purpose, Scope, Definitions, References, Overview. Section 2 "PFUCA" = Perspective, Functions, Users, Constraints, Assumptions. Section 3 "EF-PLDS" = External interfaces, Functions, Performance, Logical database, Design constraints, System attributes.
Common mistake: Writing detailed requirements in section 2. Section 2 only gives background and a summary; every testable detail goes in section 3. (IEEE 830-1998 has since been superseded by ISO/IEC/IEEE 29148, but syllabi and textbooks still teach the 830 outline.)
Quick recall 1 Introduction (PSDRO) → 2 Overall description (PFUCA) → 3 Specific requirements (EF-PLDS) → Appendices, Index.

2.14 Short answers (1 mark)

Define requirement engineering.
Systematic use of principles, techniques and tools to elicit, analyse, document, review and manage software requirements. Its output is the SRS.
Differentiate functional and non-functional requirements.
Functional: what the system does (e.g. compute result). Non-functional: how well it does it: performance, security, usability (e.g. result in 3 seconds).
What are known, unknown and undreamt requirements?
Known: stated by the stakeholder. Unknown: forgotten because not needed now or needed by another stakeholder. Undreamt: stakeholder cannot imagine them due to limited domain knowledge.
Who is a stakeholder?
Any person or group affected by or having influence on the system: customer, users, developers, testers, managers.
Expand FAST and QFD.
FAST: Facilitated Application Specification Technique. QFD: Quality Function Deployment.
List the lists prepared in a FAST meeting.
Objects (around, produced, used by the system), services, constraints, and performance criteria. Sub-teams then write mini-specifications.
What are normal, expected and exciting requirements?
Normal: explicitly stated. Expected: implicit, so basic that customers do not state them. Exciting: beyond customer expectations, delight when present (QFD).
What is a use case? Name its diagram symbols.
Sequence of actor-system interactions giving a result of value. Actor = stick figure, use case = ellipse, system boundary = rectangle, association = line.
Draw / name the symbols of a DFD.
Process = circle, external entity = rectangle, data store = two parallel lines (open box), data flow = named arrow.
What is a context diagram?
Level 0 DFD showing the entire system as a single process with all external entities and data flows; it defines the system boundary.
What is balancing in DFD?
The data flows entering and leaving a parent process must match the net inputs and outputs of its child (lower level) diagram.
Define data dictionary.
A repository of definitions of all data flows, data stores and data items of the DFD, with composition, aliases and usage, written in notation such as =, +, [ | ], { }, ( ).
What does { } and ( ) mean in a data dictionary?
{ } = iteration (repeated), ( ) = optional. Example: marksheet = roll_no + {subject_code + marks}; name = first + (middle) + last.
Define cardinality in ER diagram.
Maximum number of entity instances on one side that can be related to one instance on the other side: 1:1, 1:N or M:N.
What is a weak entity?
An entity that cannot be uniquely identified by its own attributes and depends on an owner entity via an identifying relationship. Drawn as a double rectangle.
What is an SRS?
Software Requirements Specification: document describing completely WHAT the software will do, not HOW; the agreement between customer and developer.
List characteristics of a good SRS.
Correct, unambiguous, complete, consistent, ranked for importance/stability, verifiable, modifiable, traceable (IEEE 830).
Name the three main sections of an IEEE 830 SRS.
1 Introduction, 2 Overall description, 3 Specific requirements (plus appendices and index).

2.15 Long-answer frames (8 marks)
