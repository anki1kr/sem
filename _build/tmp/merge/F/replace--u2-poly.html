2.11 Polymorphism: overloading and overriding

One word, many forms: "pay" works differently for UPI, card and cash, but you just say pay. (ek naam, kai roop)

Definition: Polymorphism is the ability of one method name (or reference) to take many forms. In Java it is of two kinds: compile-time polymorphism, achieved by method overloading, and run-time polymorphism, achieved by method overriding with dynamic method dispatch.

(a) Compile-time polymorphism: method overloading

  • Overloading: same method name, different parameter list (number, type or order) in the same class.
  • The compiler picks the version by matching the arguments, so it is decided before the program runs.
  • Return type alone cannot overload: int f() and double f() is an error.
  • Java does not allow user-defined operator overloading (only built-in + joins strings).
class Calculator {
    int add(int a, int b) {              // 2 int parameters
        return a + b;
    }
    int add(int a, int b, int c) {       // different NUMBER of parameters
        return a + b + c;
    }
    double add(double a, double b) {     // different TYPE of parameters
        return a + b;
    }
}

public class OverloadDemo {
    public static void main(String[] args) {
        Calculator c = new Calculator();
        System.out.println(c.add(2, 3));       // compiler picks add(int,int)
        System.out.println(c.add(2, 3, 4));    // picks add(int,int,int)
        System.out.println(c.add(2.5, 1.5));   // picks add(double,double)
    }
}

(b) Run-time polymorphism: method overriding and dynamic method dispatch

  • Overriding: child class gives its own body for a method with the same signature as the parent's.
  • Dynamic method dispatch: a parent-type reference can hold a child object (Payment p = new UpiPayment();); the JVM calls the method of the actual object at run time, not of the reference type.
  • @Override annotation asks the compiler to check that a method really overrides.
class Payment {
    void pay(int amt) { System.out.println("Paying Rs." + amt); }
}

class UpiPayment extends Payment {
    @Override
    void pay(int amt) { System.out.println("Paying Rs." + amt + " by UPI"); }
}

class CardPayment extends Payment {
    @Override
    void pay(int amt) { System.out.println("Paying Rs." + amt + " by card"); }
}

public class DispatchDemo {
    public static void main(String[] args) {
        Payment p;                   // parent-type reference
        p = new UpiPayment();
        p.pay(200);                  // decided at RUN time: UpiPayment's pay
        p = new CardPayment();
        p.pay(500);                  // same call, now CardPayment's pay
        p = new Payment();
        p.pay(50);
    }
}

The class notes' own overriding example — a plain override, no multi-class dispatch juggling:

class Vehicle {
    void run() {
        System.out.println("Vehicle is running");
    }
}

public class Bike2 extends Vehicle {
    void run() {                        // same name, same parameters as Vehicle's run()
        System.out.println("Bike is running safely");
    }
    public static void main(String[] args) {
        Bike2 obj = new Bike2();
        obj.run();                       // only the overridden version executes
    }
}
Bike is running safely
Common mistake: the notes add here, "when you write two or more classes in a single file, the file is named upon the class that contains the main method." The precise rule is about public, not about main: if one class in the file is public, the file must be named after THAT class, whether or not it has main; only when no class in the file is public can the file take any name at all (you then simply run whichever class has main). Bike2.java above is named after its public class Bike2, which also happens to hold main — that overlap is what makes the two rules look identical in a single example.

Rules of method overriding

  • Same name and same parameter list as the parent method.
  • Return type same, or a subclass of it (covariant return).
  • Access cannot be more restrictive (a public method cannot become private).
  • final, static and private methods cannot be overridden (a static method with the same signature only hides the parent's).
  • Needs inheritance (IS-A); constructors cannot be overridden.
Common mistake: the notes' rule here is "static or final method cannot be overridden." Add private to that same list. There is also a sharper point hiding inside this rule: if a subclass declares a static method with the exact signature of a static method in its parent, that is method hiding, not overriding — Java decides which one runs from the reference type at compile time, unlike genuine overriding, which is decided from the object type at run time. Proof below.
class Parent2 {
    static void greet() { System.out.println("Parent2 static greet"); }
}

class Child2 extends Parent2 {
    static void greet() { System.out.println("Child2 static greet"); }  // HIDES, does not override
}

public class HidingDemo {
    public static void main(String[] args) {
        Parent2 p = new Child2();
        p.greet();                // resolved by p's REFERENCE type (Parent2), not its object type
        Child2.greet();
    }
}
Parent2 static greet
Child2 static greet
  • p is declared Parent2 but refers to a Child2 object; because greet() is static, Java uses p's declared type, so Parent2's greet() runs. Compare this with DispatchDemo above, where the instance method pay() used the object's real type instead of the reference type.

Common mistake: with Payment p = new UpiPayment(); you can only call methods that exist in Payment; the child version runs, but child-only methods are not visible through p.
Quick recall Overloading = compile time, different parameters; overriding = run time, same signature, parent reference picks child method; a matching static method in the child HIDES the parent's (reference decides), it never overrides it.
