2.14 Packages

Packages are folders for classes, like keeping college notes in separate subject folders so two files named "Unit1" never clash. (classes ka folder)

Definition: A package is a named group of related classes, interfaces and sub-packages that provides a namespace (avoids name clashes), access protection and easy reuse. Packages are of two types: built-in (Java API) and user-defined.
Built-in packageContains (examples)
java.langString, Math, System, Object (imported automatically)
java.utilScanner, ArrayList, Arrays
java.ioFile, InputStreamReader, IOException
java.awtGUI classes such as Button, Frame
java.netURL, Socket (networking)
java.sqlConnection, ResultSet (database)

The notes draw the built-in tree one level deeper — each sub-package holding its own classes:

Creating a user-defined package

  • Write package name; as the first statement of the source file.
  • Package name = folder name; college.exam means folder college/exam. Use lowercase.
  • Compile with javac -d . File.java: -d tells javac where to put the class file and it creates the package folder automatically (. = current folder). The syntax is really javac -d <directory> <file>, so -d can equally name any other path, e.g. javac -d d:/madhu File.java.
  • Classes used from outside the package must be public.

Step 1: file project/Greet.java, the package member:

package mypack;                       // must be the first statement

public class Greet {                  // public so other packages can use it
    public void hello(String name) {
        System.out.println("Hello " + name);
    }
}

Step 2: file project/UsePack.java, a class outside the package that imports it:

import mypack.Greet;                  // single-type import (or: import mypack.*;)

public class UsePack {
    public static void main(String[] args) {
        Greet g = new Greet();
        g.hello("Riya");
    }
}

Step 3: commands, run from inside project/. The first creates folder mypack holding Greet.class; the last runs the program, which prints Hello Riya.

javac -d . Greet.java
javac UsePack.java
java UsePack

Running a class that is itself inside a package — UsePack above is an outside class that only imports the package; the notes also show the other case, where the class you run IS the package member. Then you launch it with the package's fully qualified name:

package mypack;

public class Simple {
    public static void main(String[] args) {
        System.out.println("Welcome to package");
    }
}
javac -d . Simple.java
java mypack.Simple
Welcome to package
  • No plain java Simple here — Simple.class now lives inside folder mypack, so the JVM needs package name . class name to find it.

Ways to use a class from another package — three methods:

WaySyntaxImports
1. Fully qualified namepack.A obj = new pack.A();No import statement needed at all
2. Single-type importimport pack.A;Only that one class
3. On-demand (wildcard) importimport pack.*;All public classes of the package (not its sub-packages)

Method 1 — fully qualified name, no import at all:

A.java (package pack):

package pack;

public class A {
    public void msg() {
        System.out.println("Hello");
    }
}

B.java (package mypack, a different package):

package mypack;

public class B {
    public static void main(String[] args) {
        pack.A obj = new pack.A();     // fully qualified name: no import line needed
        obj.msg();
    }
}
javac -d . A.java
javac -d . B.java
java mypack.B
Hello
  • Because every use of A is written out in full as pack.A, the compiler never needs an import line to find it. This method is mainly used when two packages have a class with the same name (e.g. both java.util and java.sql have a Date class) — writing the full name each time removes the ambiguity.

Method 2 — import just the one class you need: this is exactly the Greet / UsePack example already verified above — import mypack.Greet; brings in only that class, and the rest of the file simply writes Greet.

Method 3 — import all classes of a package with *:

Animals.java (package animals):

package animals;

class Animals {
    public void display() {
        System.out.println("All are the animals in the world");
    }
}

Humans.java (same package animals, extends Animals):

package animals;

public class Humans extends Animals {
    public void msg() {
        System.out.println("class A animals are Humans");
    }
    public void msgB() {
        System.out.println("Humans are animals with intelligence");
    }
}

World.java (package world, imports all of animals):

package world;

import animals.*;                   // every public class of animals

public class World {
    public static void main(String[] args) {
        Humans obj = new Humans();
        obj.display();
        obj.msg();
        obj.msgB();
    }
}
javac -d . Animals.java
javac -d . Humans.java
javac -d . World.java
java world.World
All are the animals in the world
class A animals are Humans
Humans are animals with intelligence

Note the reach of animals.* above: it pulls in every class of animals, but if animals had a sub-package animals.wild, that sub-package would need its own separate import — a wildcard import never reaches into sub-packages (more on this right below).

Subpackages — a package inside a package. It exists just to categorise a package further, and is named packagename.subpackagename (dot-separated), e.g. pack.subpack:

package pack.subpack;

public class Simple {
    public static void main(String[] args) {
        System.out.println("Hello subpackage");
    }
}
javac -d . Simple.java
java pack.subpack.Simple
Hello subpackage
  • javac -d . now creates two nested folders, pack/subpack/, and drops Simple.class in the inner one — the dot in the package name becomes a folder boundary, same as before.
  • Importing pack.* does not pull in pack.subpack — subpackages are never included by a wildcard import (the same point the "common mistake" note near the end of this section makes about java.util.Scanner); a sub-package must be imported on its own.

Setting CLASSPATH — needed when your .java source and the compiled .class file must live in different folders or drives, so that javac/java know where else to look:

S.java, sitting in folder D:\Madhu:

package pack;

public class S {
    public static void main(String[] args) {
        System.out.println("This is example of setting classpath");
    }
}

Compile straight into a different drive/folder, then set CLASSPATH to that folder before running:

D:\Madhu> javac -d C:\classes S.java
D:\Madhu> set classpath=C:\classes;.;
D:\Madhu> java pack.S
This is example of setting classpath
  • Verified the underlying mechanism directly: with no CLASSPATH set, running java pack.S from D:\Madhu fails with Could not find or load main class pack.S, because the class file is not there and not on the current folder; once CLASSPATH points at C:\classes, the same command finds pack\S.class and runs it.
  • Adding .; to the CLASSPATH value (as above) keeps the current folder searchable too, so classes that ARE alongside you still run normally.

How many public classes can one package hold?

Common mistake: "In Java there can be only one public class in a package" is WRONG. The real rule is one public class per SOURCE FILE, and that file must be named after it. A package can hold as many public classes as you like — just keep each one in its own file, all saved under the same package name.

Alpha.java:

package madhu;

public class Alpha {
    public void show() {
        System.out.println("Class Alpha in package madhu");
    }
}

Beta.java:

package madhu;

public class Beta {
    public static void main(String[] args) {
        Alpha a = new Alpha();      // same package: no import needed
        a.show();
        System.out.println("Class Beta in package madhu");
    }
}
javac -d . Alpha.java
javac -d . Beta.java
java madhu.Beta
Class Alpha in package madhu
Class Beta in package madhu
  • Alpha and Beta are both public, both in package madhu, and both compile and run fine — because each has its OWN file named after it. This is also the earlier A.java/B.java Method-1 example's shape, just within a single package instead of two.
  • Classes in the same package never need an import to use each other — Beta uses Alpha directly.

Access protection across packages (Yes = accessible):

Accessed fromprivatedefaultprotectedpublic
Same classYesYesYesYes
Same package, subclassNoYesYesYes
Same package, non-subclassNoYesYesYes
Other package, subclassNoNoYesYes
Other package, non-subclassNoNoNoYes
Mnemonic Yes-count down the columns is 1-3-4-5: private 1 row, default 3, protected 4, public all 5.
  • Advantages: avoids name conflicts, groups related classes, access control, reusability, easier maintenance.
  • java.lang is imported automatically in every program.
  • Order in a file is always package statement, then import statement(s), then class declarations — never the other way round:
package statement;    // 1st
import statement;     // 2nd
class statement;      // 3rd
Common mistake: thinking import java.*; imports everything. The * never includes sub-packages, so java.util.Scanner still needs import java.util.*; or import java.util.Scanner;.
Quick recall package = folder of classes (+ sub-packages); package first line, javac -d directory, run a package member with java pkg.Class. Import: fully-qualified name (none needed), single-class, or * (never sub-packages). Subpackage = dot-separated nested folder. CLASSPATH points java/javac at a class file living elsewhere. One public class per FILE, not per package — a package can hold many, each in its own file.
