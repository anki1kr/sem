2.7 Data Ingestion

Ingestion is the front door: getting data from its sources into your data system, ideally automatically. (data ko system ke andar laana)

Definition: Data ingestion is the process of getting data from its sources into the data system being built or used (for storage and processing), either in batches or as a continuous stream, according to an ingestion policy.
  • Batch ingestion: data collected and loaded at intervals (e.g. nightly load of the day's sales). (ikattha karke ek saath)
  • Streaming (real-time) ingestion: each record flows in as it is produced (sensor readings, tweets, clicks). (lagatar behta hua)
  • Automation: at big data scale, ingestion must be automated, not manual uploads.
  • Infrastructure questions to ask before designing ingestion:
    • How many data sources are there, and will the number grow?
    • How large is each data item, and at what rate does data arrive?
    • What to do with bad data (reject, repair, or flag and keep)?
    • What to do when data arrives too fast / too much, or too little?
  • Ingestion policy / error policy: e.g. hospital medical records are never discarded; errors are flagged but data retained. For a high-volume social-media stream, bad records may simply be dropped.
  • Typical tools: Apache Kafka / Flume (streams, logs), Sqoop (relational DB to Hadoop).

Example (ingestion rate of smart meters)
10,00,000 meters, 1 reading every 15 min → readings/day per meter = 24 × 60 / 15 = 96
Total readings/day = 10,00,000 × 96 = 9,60,00,000 (96 million)
Size at 200 bytes each = 96,000,000 × 200 = 19,200,000,000 B = 19.2 GB/day (1 GB = 109 B)
Rate = 96,000,000 / 86,400 s = 1111.1 readings per second (1 decimal)
≈ 1111 readings/s and 19.2 GB/day, so a streaming ingestion system is needed.

More Ingestion Tools

  • Apache NiFi: automates and manages data flows between systems (drag-and-drop pipeline routing).
  • AWS Kinesis / Azure Event Hubs: managed cloud services for ingesting real-time streams at scale.

Data Ingestion Techniques: ETL, ELT and CDC

  • Choice of technique depends on: the business requirement, the complexity of the data, and the infrastructure already in place.
  • ETL (Extract, Transform, Load): data is extracted, cleaned/transformed into a consistent format, then loaded into storage such as a data warehouse. Best when structured, ready-to-analyse data is the priority (reports, strict quality rules, relational databases).
  • ELT (Extract, Load, Transform): data is extracted and loaded into the target (a data lake / cloud platform) in raw form first, and transformed later, on demand, inside that system. Best for large volumes of unstructured / semi-structured data where transformation can wait.
  • CDC (Change Data Capture): detects and captures only the changes (insert / update / delete) made at a source and replicates just those changes to the target in real time, instead of reloading the whole dataset. Used for high-frequency trading, e-commerce, or keeping systems in sync with minimal lag.

Data Sources for Ingestion: Structured, Semi-structured, Unstructured

  • Structured data: highly organised, fixed schema, rows and columns (relational databases). Easiest to ingest — the schema itself rejects bad values.
  • Semi-structured data: some organisation via tags/markers (JSON, CSV, NoSQL records) but no rigid schema; flexible; needs parsing/transformation.
  • Unstructured data: no defined structure at all (images, video, audio, documents); hardest to process; usually stored raw in a data lake and analysed with ML / NLP.

Challenges in Data Ingestion

  • Handling large volumes: data keeps growing (especially real-time IoT / social-media streams), so the pipeline must scale continuously.
  • Data quality and consistency: multiple sources arrive in different formats or with conflicts; validation is needed at ingestion time, not only later.
  • Security and compliance: personal data (name, address, payment details) must be encrypted and access-controlled during ingestion to meet regulations such as GDPR or HIPAA.
  • Latency requirements: when a use case needs instant insight, the pipeline must process and expose data with very little delay.
Mnemonic Ingestion technique choice = "B-C-I": Business need, data Complexity, existing Infrastructure. Ingestion challenges = "V-Q-S-L": Volume, Quality, Security, Latency.
Mnemonic Ingestion questions "S-S-R-B-T": Sources (how many, growing?), Size, Rate, Bad data, Too much / too little.
Common mistake: confusing ingestion with storage. Ingestion moves data in; storage is where it rests.
Quick recall Ingestion = bringing data in; batch vs stream; ETL transforms before loading, ELT after, CDC replicates only the changes; sources are structured/semi-structured/unstructured; plan for volume, quality, security and latency.
