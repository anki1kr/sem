1.9 HDFS: Hadoop Distributed File System

HDFS cuts a huge file into big blocks and keeps 3 copies of each block on different machines.

Definition: HDFS is Hadoop's distributed file system that stores very large files as fixed-size blocks across many DataNodes, replicating each block for fault tolerance, and is designed for write-once, read-many, high-throughput streaming access.
  • NameNode (master): stores the metadata: namespace (directory tree), file → block list, block → DataNode locations, permissions. It does not store the actual data. (register rakhta hai, maal nahi)
  • DataNode (slave): stores the actual blocks on local disk, serves read/write requests, and sends a heartbeat (every 3 s by default) and periodic block reports to the NameNode. A cluster may have anywhere from a handful of DataNodes up to 500 or more; more DataNodes means more storage and more parallel I/O.
  • Secondary NameNode: periodically merges the edit log into the fsimage (checkpointing) so the NameNode restarts faster. It is not a hot standby. In HA setups a Standby NameNode does this job.
  • Block: a file is split into fixed-size blocks; default 128 MB in Hadoop 2.x/3.x (64 MB in 1.x), configurable via dfs.blocksize. The last block holds only the remaining bytes, so it can be smaller.
  • Replication factor: default 3 (dfs.replication). Rack-aware default placement: 1st replica on the writer's node (or a random node), 2nd on a node in a different rack, 3rd on a different node in the same rack as the 2nd. A rack is simply the physical group of nodes (commonly on the order of 30–40 machines) sharing one network switch; choosing the closest rack for a read/write cuts network traffic.
  • If a DataNode stops sending heartbeats, the NameNode marks it dead and re-replicates its blocks from surviving copies.
  • Write-once, read-many: files can be appended but not edited in the middle; good for large sequential reads, poor for random updates.
  • Hadoop 3 adds optional erasure coding, which gives fault tolerance with less storage overhead than 3× replication.
  • fsimage and edit log: the NameNode keeps its metadata in two files. The fsimage is a complete snapshot of the namespace at one point in time; the edit log is an append-only record of every change (create, rename, append, ...) since that snapshot. On restart the NameNode reloads the fsimage and replays the edit log to rebuild its current state, instead of writing a brand-new snapshot on every single change.
  • The Secondary NameNode periodically pulls the edit log over RPC and merges it into its own copy of the fsimage (this is exactly what "checkpointing" means), so a restarted NameNode has a shorter edit log to replay and recovers faster — but, as above, it still cannot take over automatically the way a Standby NameNode in HA mode can.
  • Because the NameNode keeps this state in memory, production clusters typically also persist it to two local disks (in case one disk fails) and to an NFS-mounted volume (in case the whole machine fails).
  • Terms: Heartbeat — the signal a DataNode sends the NameNode at regular intervals; missing heartbeats mark it dead. Balancing — after a DataNode dies, its blocks become under-replicated, so the NameNode signals DataNodes holding surviving copies of those blocks to replicate them elsewhere, restoring even distribution. Replication — the copying itself is carried out by the DataNodes, not the NameNode. Rule: no two replicas of the same block are ever placed on the same DataNode.
Example A 500 MB file, block size 128 MB, replication factor 3:
Number of blocks = ceil(500 / 128) = ceil(3.906...) = 4
Block sizes = 128 + 128 + 128 + (500 − 3 × 128) = 128, 128, 128, 116 MB
Block replicas stored = 4 × 3 = 12
Raw disk used = 500 × 3 = 1500 MB (the last block uses only 116 MB per copy, not 128)
4 blocks, 12 replicas, 1500 MB raw storage

Features of HDFS

  • Distributed data storage across many DataNodes rather than one machine.
  • Blocks reduce seek time: splitting a huge file into fixed blocks makes parallel reads/writes far faster than seeking through one giant file on a single disk.
  • High availability: the same block sits on multiple DataNodes, so data stays reachable even if one copy is unreachable.
  • High reliability: even if several DataNodes go down at once, work can continue as long as one replica of each block survives.
  • High fault tolerance: lost blocks are automatically re-replicated from surviving copies.

Limitations of HDFS

  • Low-latency data access: HDFS is built for high-throughput streaming reads, not millisecond-level random access, so it suits batch jobs poorly suited to interactive, low-latency lookups.
  • Small file problem: lots of small files mean lots of seeks between DataNodes to fetch each one, which is a very inefficient access pattern (and, as covered under Hadoop's limitations, it also bloats NameNode memory since every file/block is metadata there).

Mnemonic HDFS numbers "128-3-3": 128 MB block, 3 replicas, heartbeat every 3 seconds.
Common mistake: The Secondary NameNode is not a backup NameNode that takes over on failure; it only does checkpointing.
Quick recall NameNode = metadata master; DataNode = blocks; blocks 128 MB; replication 3, rack-aware; heartbeats detect failure; write-once read-many.
