Overview

What DSA Tracker is

DSA Tracker is a FastAPI + Next.js + Supabase interview-prep tracker built around 370 curated problems across 22 topics (Apna College + Love Babbar 450 + Striver A2Z), re-ordered by which of 24 target roles you're preparing for — so a frontend dev isn't grinding segment trees first.

On top of the ordering: a sheets hub (the 3 source sheets, 12 GFG-verified company sheets, and 24 role sheets), per-problem revision-confidence tracking, live sync against 7 coding platforms (LeetCode, Codeforces, CodeChef, GeeksforGeeks, AtCoder, HackerRank, GitHub), an opt-in public portfolio page (/u/<username>) with an embeddable GitHub README SVG badge, an AI roadmap + skill analysis via a free-LLM cascade, and CSV/JSON progress export and bulk import.

Mental model: one master list of problems + a per-role weighting = a personalised order. Sheets, dashboard, roadmap, and the public portfolio are all views over your progress against that ordered list.

This doc uses a handful of terms over and over. Skim these once and the rest of the page needs no further translation.

Frontend / Backend

The frontend (Next.js) is what you see and click. The backend (FastAPI) is the part you never see — it makes the decisions and does the work.

API

The waiter between the two. The frontend asks the API for something ("give me my solved count"); the backend hands the answer back as plain data (JSON), not a web page.

Database

Where everything is permanently saved (Supabase/Postgres) — your account, your progress, every problem. If it's not in the database, refreshing the page loses it.

Cookie / Session

A small note your browser keeps so the app remembers you're logged in — without it, you'd have to type your password on every single click.

Guest mode

Browse the whole app with no account at all. Nothing saves permanently, and the moment you try to save something, the app invites you to sign up.

PK / FK

A primary key (PK) is a row's unique ID card. A foreign key (FK) is another row pointing back at that ID card to say "this belongs to that person."

RLS (Row-Level Security)

A lock built into the database itself, not just the app's code — so even a leaked low-privilege key still can't read or change anyone's rows by default.

CDN / Edge

Copies of the frontend cached in data centers around the world, so the app loads fast no matter where you're opening it from.

Architecture

The big picture

In plain wordsYou tap something → the app checks if it's a page or just data → if it's data, a message quietly travels to the backend and to the database, and the answer flies back to fill your screen.
  1. You tap or type something — open the app, click a button, whatever needs an answer.
  2. The front door (Next.js) checks what kind of thing you asked for. A whole new page? It just builds it and shows you — done.
  3. If it's data (your solved count, a list of problems, your streak), it quietly sends that one small request to the engine room (FastAPI) — you never see this happen, it's not a page reload.
  4. The filing cabinet (Supabase) is asked for your data — it's the one place all of it actually lives.
  5. Sometimes the engine room also needs an AI helper — it tries a free AI model first, and if every one of them is busy or down, a simple built-in rulebook answers instead so the feature never just breaks.
  6. The answer travels all the way back through the same path and fills in your screen — usually well under a second.

Real App Router pages

Every route is its own folder under frontend-next/app/ — Server Components fetch/render by default, "use client" only where interactivity is needed.

Service layer

app/services/*.py holds the real domain logic — role reorder, revision confidence, platform sync, the AI cascade — same separation as before, just called from FastAPI routers now.

Same-origin API proxy

next.config.ts rewrites /api/* to the Render FastAPI service (API_PROXY_TARGET), so HttpOnly cookies just work with no CORS dance.

Graceful AI

If every LLM fails, a rule engine answers. The honest ai_powered flag says whether a real model actually ran.

System architecture

Full-stack view — every tier and how they talk

The diagram above is deliberately simplified. This is the same system at implementation-detail level: the actual hosting providers, the router/service split inside FastAPI, and the two backend dependencies (Redis, the AI cascade) that sit alongside the database rather than as tiers of their own.

In plain wordsSame phone → front door → engine room → filing cabinet trip as the very first diagram, just drawn with the real names on every box — plus the two helpers (Redis, the AI cascade) the engine room quietly leans on.
  • One same-origin hop, not two services glued by CORS: next.config.ts rewrites /api/* straight to the Render FastAPI URL, so the browser only ever talks to one origin and HttpOnly auth cookies work with zero CORS configuration.
  • Routers stay thin; services hold the logic: every routers_*.py file parses the request, calls a function in app/services/, and shapes the response — domain logic never lives in a router.
  • The database is only ever touched with the service-role key (never the browser's own credentials), which is why Row-Level Security is enabled with zero permissive policies on every table — a deny-by-default posture that's a no-op for the backend but blocks any leaked anon key outright.
  • Redis and the AI cascade are dependencies, not tiers: if Redis is unreachable, rate limiting falls back to an in-memory sweep; if every AI provider fails, a deterministic rule engine answers instead — the request path never dead-ends on either.
Database

Schema — 9 live tables, one hub

Every user-owned table hangs off users.id with ON DELETE CASCADE, so deleting an account cleans up everything it touched in one statement. blog_posts is the only table with no foreign key at all — it's admin-managed CMS content, not user data. An earlier profiles table (uuid primary key) existed for a Supabase-Auth-linked flow the app never finished adopting; it was dropped in migration 0005 as dead weight, not replaced.

In plain wordsThink of users as a filing-cabinet drawer with your name on it, and every other table as a folder that has to say whose drawer it belongs in. blog_posts isn't in anyone's drawer — it's a public shelf of articles anyone can read.
  • All primary keys are bigint GENERATED ... AS IDENTITY — the modern Postgres-recommended alternative to bigserial, used consistently across every table.
  • Row-Level Security is enabled on every table with zero policies — deny-by-default for the anon/authenticated roles. The backend never hits that wall because it connects with the service_role key, which bypasses RLS by design.
  • progress_revisions is a history table, not a column — overwriting a single "last confidence" column on progress would destroy exactly the per-attempt history the Revisions tab exists to show.
  • Two composite unique constraints enforce data integrity at the database level, not just in application code: (user_id, problem_id) on progress, and (user_id, entry_date) on calendar_entries.

App Router

Real routes, not one shell

This is the biggest structural change from the old Flask app: there is no more single index.html with client-side navigateTo() swapping which section is visible. Every route above is its own folder with its own page.tsx — Next.js does real server-side routing and rendering.

In plain wordsThe old site was one whiteboard that got erased and re-drawn by hand for every page. The new site is a librarian who already has a real, separate book written for every page and just hands you the right one.
  1. Old (1→2): no matter which page you asked for, your phone always talked to the same one Flask handler.
  2. Old (2→3): that handler always sent back the exact same file, index.html — every single time, whatever URL you typed.
  3. Old (3→4): a script in your browser then had to manually hide one part of that file and show another — nothing new ever actually arrived from the server.
  4. Now (1→2): your phone still asks for a URL, but a router looks at it like a librarian checking a call number.
  5. Now (2→3/4/5): the router sends back a real, separate, already-written file for that exact page — dashboard, problems, and profile are three different books, not one book with sticky notes.
browser hits /dashboard └─ Next.js matches app/dashboard/page.tsx └─ "use client" component mounts, calls apiFetch("/api/dashboard") └─ same-origin rewrite → FastAPI → DashboardService → Supabase

Shared chrome (sidebar, topbar, guest-signin prompt, onboarding modal) lives in app/components/app-shell.tsx, which wraps every route except the standalone auth pages and the landing page.

Auth, guest mode & security

How sign-in, guests, and protection work

  • Sessions: real Supabase Auth — HttpOnly cookies, Google OAuth via a locked-down redirect base.
  • Guest mode: a suits_guest cookie lets an anonymous visitor browse a shared demo account read-only. Every write endpoint depends on require_write_user_id (403s a guest) instead of get_current_user_id (resolves a guest to the demo account) — reads still work, writes prompt sign-up.
  • Anonymous auto-bootstrap: a fresh visitor's first 401'd GET silently starts a guest session instead of showing an error wall — except for a short window right after an explicit logout, where it's deliberately suppressed (fixed 2026-08-08: a page's own in-flight request resolving into a 401 just after logout was re-enrolling the user as a guest instead of landing them on /login).
  • DEV_BYPASS: dev-only, auto-logs-in as user 1. Production refuses to boot if it's on — api/deps.py::validate_production_env().
  • Rate limits: Redis-backed pipeline INCR+EXPIRE, falls back to an in-memory time-swept limiter.
  • Auth fails closed: a lookup error denies access, never grants it.
In plain wordsSigning out sets a tiny 8-second "just logged out" timer. If any leftover request fails during those 8 seconds, the app knows why and just shows you the login page — it doesn't panic and mistake you for a brand-new stranger.
  1. You tap Sign out.
  2. The app deliberately forgets you — clears your cookies — and starts a tiny 8-second "I just signed out" timer in the background.
  3. Sometimes an older request that was already in the middle of loading (say, your dashboard was still fetching your streak) finishes just after your cookies were cleared, so it gets rejected too — but for an unrelated, harmless reason.
  4. The app asks: did that rejection happen inside the 8-second window? That's the one clue that tells the two situations apart.
  5. If yes — it was almost certainly that harmless leftover request, so the app just shows you the login page like you'd expect.
  6. If no — it's treated as a real, brand-new visitor browsing for the first time, and a read-only guest session quietly starts so they're not stuck at an error wall.
