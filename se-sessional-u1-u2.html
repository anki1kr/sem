Unit IIntroduction

What software is, why its development went into "crisis", and the life cycle models engineers use to build it in a planned way.

1.1 Software and Software Engineering

Software is not just code: it is the programs plus the documents and procedures that make them usable. (code + kaagaz + chalane ka tareeka)

Definition (Software): Software is a collection of computer programs, documentation and operating procedures that together make a computer system perform a useful task.
Definition (Software Engineering, IEEE): Software engineering is "the application of a systematic, disciplined, quantifiable approach to the development, operation and maintenance of software; that is, the application of engineering to software." (IEEE Std 610.12)
  • Software engineering is an engineering discipline covering every stage from requirements to maintenance, not only coding. (sirf coding nahi, pura process)
  • Its goal: deliver high-quality software on time, within budget, that meets user needs and is easy to maintain.
  • Pressman calls SE a layered technology: quality focus (base) → process → methods → tools.
  • Types of software (Pressman): system software, application software, engineering/scientific, embedded, product-line, web applications, AI software.
BasisProgramSoftware (product)
SizeSmall, usually one moduleLarge, many modules
DeveloperSingle personTeam of developers
UsersAuthor himself / few usersMany unknown users
DocumentationLittle or noneFull: SRS, design, manuals
User interfaceNot importantCarefully designed
DevelopmentAd-hoc, personal styleSystematic, follows a process model
FormulaCode onlyPrograms + documentation + operating procedures

Software myths (Pressman) are false beliefs that cause bad decisions:

TypeMythReality
Management"If we are behind schedule, add more programmers."Adding people to a late project makes it later (new people need training time).
Management"We have a book of standards, that is enough."A book nobody uses or updates does not improve quality.
Customer"A general statement of objectives is enough to start coding."Vague requirements are a major cause of failure.
Customer"Changes can be easily accommodated because software is flexible."Cost of change grows sharply in later phases.
Practitioner"Once the program works, our job is done."Most effort is spent after first delivery (maintenance).
Practitioner"The only deliverable is the working program."Documentation and test results are also deliverables.
Mnemonic Software = P-D-O : Programs, Documentation, Operating procedures. Myths come from M-C-P : Management, Customer, Practitioner.
Common mistake: Writing "software = program". A program is only one of the three parts of software.
Quick recall IEEE: SE = systematic, disciplined, quantifiable approach to develop, operate, maintain software.

1.2 Software Characteristics

Software behaves very differently from hardware: it is engineered, never manufactured, and it does not wear out. (ghista nahi, par bigadta hai)

Definition: Software characteristics are the properties that distinguish software from physical (hardware) products and that decide how it must be developed and maintained.
  • Developed or engineered, not manufactured: cost is in engineering (design, coding, testing), not in production; copying software costs almost nothing. (factory mein nahi banta)
  • Does not wear out: hardware follows the bathtub curve (early defects, steady period, wear-out due to dust, heat, vibration). Software has no physical wear, so its idealized curve falls and stays flat.
  • But software deteriorates: each change (maintenance) can add new defects, so the actual curve shows spikes and the minimum failure rate slowly rises.
  • Custom built: most software is still built for a specific need, although the industry is moving towards component reuse (libraries, frameworks, APIs).
  • No spare parts: a failed hardware part is replaced; a software failure means a design/coding error, so maintenance is more complex.
  • Flexible (Aggarwal & Singh): software is easy to change, which also makes it easy to change badly.
BasisHardwareSoftware
ProductionManufacturedDeveloped / engineered
WearWears out with timeDoes not wear out, but deteriorates due to changes
Failure curveBathtub curveIdealized flat curve; actual curve with spikes
RepairReplace spare partFix the design/code, no spare parts
Copy costHigh (material, labour)Almost zero
Example
A UPI app works fine for months. An update adds a new feature and accidentally breaks bill payment.
Nothing physical wore out; the failure came from a change. This is the spike on the actual curve.
Software deteriorates due to change, not due to wear.
Mnemonic E-W-C : Engineered (not manufactured), does not Wear out, Custom built (moving to component reuse).
Common mistake: Drawing the bathtub curve for software. The bathtub curve is for hardware; software gets the idealized and actual curves.
Quick recall Hardware wears out (bathtub). Software does not wear out but deteriorates, because every change can add defects.

1.3 Software Crisis

In the 1960s computers got powerful, but software projects kept failing: late, costly, buggy. That mess was named the software crisis. (project late, budget se bahar, bugs bhare)

Definition: Software crisis is the set of problems faced in developing software: projects running over budget, behind schedule, of poor quality, hard to maintain and not meeting user requirements.
  • Origin: the term became widely used around the 1968 NATO Software Engineering Conference, where the name "software engineering" was also promoted.
  • Symptoms:
    • Over budget: actual cost far above estimate.
    • Late: delivery dates missed repeatedly.
    • Poor quality: unreliable, many bugs after delivery.
    • Unmaintainable: code difficult to change, fix or extend.
    • Requirement mismatch: software does not do what the user wanted.
    • Hardware cost falling while software cost rising as a share of system cost.
  • Causes:
    • Growing size and complexity of software.
    • No systematic process; ad-hoc "code and fix" style. (jaise mann kiya waise likha)
    • Poor requirement gathering and changing requirements.
    • Poor estimation of effort, cost and time; weak project management.
    • Little testing, little documentation, poor communication with users.
    • Shortage of trained people; programmers treated software like a personal art.
  • Solution: software engineering — defined process models, requirement analysis, design methods, testing, quality assurance, project management and tools (CASE).
Example
A college orders an admission portal "in 2 months". No written requirements; coding starts on day 1.
Fee rules change midway, the team patches code, testing is skipped, and the portal crashes on result day.
Late + over budget + poor quality + requirement mismatch = software crisis in miniature.
Mnemonic Symptoms "BLQMR" : over Budget, Late, poor Quality, hard to Maintain, Requirement mismatch.
Quick recall Crisis = late, costly, buggy, unmaintainable software. Cause = no discipline. Cure = software engineering.

1.4 Software Process

A process is the recipe: the ordered set of activities followed to turn a user's need into working software. (software banane ki vidhi)

Definition: A software process is a set of activities, actions and tasks, with their associated results, that are carried out to develop and maintain a software product.
  • Five generic framework activities (Pressman):
    • Communication: talk with the customer, gather requirements.
    • Planning: estimate cost, schedule, risks, resources.
    • Modeling: analysis model and design model. (banane se pehle naksha)
    • Construction: code generation and testing.
    • Deployment: deliver to customer, get feedback, support.
  • Umbrella activities run through the whole project: project tracking and control, risk management, software quality assurance, technical reviews, measurement, software configuration management, reusability management, work product preparation.
  • Aggarwal & Singh view: process = the way we produce software; it decides quality, cost and schedule of the product.
  • A process model (life cycle model) is a simplified representation of a process that fixes the order of activities.
BasisProcessProjectProduct
MeaningSet of activities to build softwareA time-bound effort to build one specific softwareThe software (code + documents) delivered
Question answeredHow is it built?What, when, by whom, with what budget?What is delivered?
LifeReused across many projectsHas start and end dateUsed and maintained after delivery
ExampleWaterfall / spiral process"Build hostel portal by March"The hostel portal itself
Mnemonic Framework activities "C-P-M-C-D" : "Come, Plan, Make, Code, Deliver" = Communication, Planning, Modeling, Construction, Deployment.
Common mistake: Listing testing as a separate framework activity. In Pressman's generic framework, testing is part of Construction (code + test).
Quick recall Process = activities to build software: Communication, Planning, Modeling, Construction, Deployment + umbrella activities.

1.5 Characteristics of a Good Software Process and a Good Software Product

A good process makes good software likely; a good product is judged by how it runs, moves and changes. (achha tareeka, achha maal)

Definition: Process characteristics are the qualities that make a software process effective and usable by a team; product characteristics (quality attributes) are the qualities that make the delivered software acceptable to users and maintainers.
  • Understandability: to what extent the process is explicitly defined and easy to understand.
  • Visibility: activities end in clear results (documents, reviews) so progress is visible outside.
  • Supportability: to what extent CASE tools can support the activities.
  • Acceptability: the defined process is acceptable to and usable by the engineers.
  • Reliability: process errors are avoided or trapped before they become product errors.
  • Robustness: the process can continue despite unexpected problems.
  • Maintainability: the process can evolve with changing organisational needs.
  • Rapidity: how fast a system can be delivered from a given specification.

This eight-point list originates from Sommerville and is the one reproduced in Indian university texts (including Aggarwal & Singh based notes).

  • Operational (how well it runs): correctness, efficiency (budget, time, memory), usability, reliability, integrity, safety, security, functionality. (chalte waqt kaisa hai)
  • Transition (how well it moves to a new environment): portability, interoperability, reusability, adaptability.
  • Maintenance (how well it can be changed): maintainability, flexibility, extensibility, scalability, modularity.
  • These three views follow McCall's quality model (product operation, product transition, product revision); some books say "revision" instead of "maintenance".
BasisGood process characteristicsGood product characteristics
Applies toThe way software is builtThe software delivered
Judged byDevelopment team, managementUsers and maintainers
ExamplesVisibility, rapidity, robustnessCorrectness, portability, maintainability
Mnemonic Process: "U-V-S-A R-R-M-R" : "Understand, View, Support, Accept, then Rely, be Robust, Maintain, be Rapid". Product: O-T-M : Operational, Transition, Maintenance.
Common mistake: Mixing the two lists. Portability and correctness are product qualities; visibility and rapidity are process qualities.
Quick recall Process: understandability, visibility, supportability, acceptability, reliability, robustness, maintainability, rapidity. Product: operational, transition, maintenance.

1.6 Software Life Cycle (SDLC) and Life Cycle Models

Every software is born, grows, is used, changed, and finally retired. The SDLC names those stages. (software ka janm se retirement tak)

Definition: The software life cycle is the period from the conception of a software product until it is retired. A software life cycle model (process model) is a descriptive and diagrammatic representation of the life cycle that identifies all activities and the order in which they are done.
  • Feasibility study: is the project technically and financially worth doing?
  • Requirement analysis & specification: understand and document needs in the SRS.
  • Design: architecture, modules, data structures (from SRS to design document).
  • Coding & unit testing: write each module and test it alone.
  • Integration & system testing: combine modules and test the full system.
  • Maintenance: corrective (fix bugs), adaptive (new environment), perfective (improvements). Usually the longest and costliest phase.
  • Why a model is needed: gives discipline, clear entry/exit criteria for each phase, helps managers track progress and assign work. (sab ko pata ho kya, kab, kaun karega)
  • Build and fix model (Aggarwal & Singh): code, then fix repeatedly, with no specification or design. Fine only for tiny programs; it is the "no model" baseline.

Books group models differently: Aggarwal & Singh and Pressman put prototyping and spiral under evolutionary models; some syllabi also call the incremental model "evolutionary". The models themselves are the same.

Quick recall SDLC: feasibility, requirements, design, coding, testing, maintenance. A life cycle model fixes the order of these activities.

1.7 Waterfall Model (Classical and Iterative)

Like water falling down steps: finish one phase fully, then go down to the next, never back up. (ek step khatam, phir agla)

Definition: The waterfall model (classical life cycle / linear sequential model) is a model in which development proceeds sequentially through phases, each phase starting only after the previous one is complete and its output document is approved. It is usually attributed to W. W. Royce (1970).
  • Phases (Aggarwal & Singh):
    • Requirement analysis & specification: output = SRS document.
    • Design: output = SDD (software design document).
    • Implementation & unit testing: modules coded and tested individually.
    • Integration & system testing: modules combined, whole system tested.
    • Operation & maintenance: software used, errors corrected, enhancements made.
  • Classical waterfall: strictly one-way; it assumes no mistakes are ever found in earlier phases. It is an idealistic, theoretical model.
  • Iterative waterfall: adds feedback paths from every phase to the previous phases, so an error found later can be corrected where it was introduced. No feedback to the feasibility study. (galti mile to peeche jaa ke theek karo)
  • Document-driven: each phase ends with a document that is reviewed and signed off.
AdvantagesDisadvantages
Simple, easy to understand and explainRequirements must be fully known at the start; real projects rarely have this
Clear milestones and documents; easy to manageWorking software appears only late in the life cycle
Each phase is reviewed before the next beginsChanges are costly once a phase is frozen
Works well for small, well-understood projectsPoor risk handling; errors found late are expensive
Good documentation for maintenanceCustomer sees nothing until the end; "blocking states" as teams wait for previous phase
BasisClassical waterfallIterative waterfall
FeedbackNoneFeedback paths to previous phases
Error correctionNot planned forErrors fixed in the phase where they occurred
Practical useTheoretical / idealisticUsed in practice

When to use: requirements are clear, complete and stable; technology is well known; project is short or similar to earlier ones; e.g. converting a fixed paper form into a small payroll system.

Mnemonic Phases "R-D-I-I-O" : "Rahul Does Its Integration Once" = Requirements, Design, Implementation, Integration, Operation.
Common mistake: Saying the classical waterfall allows going back. Only the iterative waterfall has feedback arrows.
Quick recall Waterfall = sequential phases, document at each end, needs fixed requirements. Iterative waterfall = same + feedback paths.

1.8 Prototype Model

When the customer says "I'll know it when I see it", build a quick working sample first and let them try it. (pehle namoona dikhao, phir asli banao)

Definition: The prototyping model builds a working prototype (a partial, quick, low-cost version with limited functionality) of the system, gets customer evaluation, refines it repeatedly until requirements are clear, and then engineers the actual product.
  • Requirements gathering: developer and customer define overall objectives and known needs.
  • Quick design: focuses on what the user sees (screens, input/output formats).
  • Build prototype: quick and dirty; efficiency and full error handling are ignored. (jaldi ka kaam chalau version)
  • Customer evaluation: user tries it and gives feedback.
  • Refine: requirements updated, prototype changed; loop until customer is satisfied.
  • Engineer product: final SRS written, then the real system is designed, coded and tested properly (often in waterfall style).
BasisThrowaway (rapid) prototypingEvolutionary prototyping
Fate of prototypeDiscarded after requirements are clearRefined step by step into the final system
PurposeClarify requirementsDeliver a working system gradually
Code qualityQuick, low quality is acceptableMust be good quality from the start
Best forPoorly understood requirementsWell-understood parts built first, rest evolves
AdvantagesDisadvantages
Customer sees a working model early; better requirementsCustomer may think the prototype is the final product and want it delivered as is
Missing or confusing features found earlyExtra cost and time of building prototypes
High user involvement, higher satisfactionDevelopers may keep poor quick choices in the final system
Reduces risk of requirement mismatchToo many refine cycles if not controlled

When to use: requirements unclear or likely to change; user interface heavy systems; new kind of system; customer not sure what he wants.

Example
A canteen wants a pre-order app but cannot describe the screens.
Team builds clickable menu and cart screens in a week, students try it, ask for "UPI option" and "pickup time slot".
Prototype fixed the requirements before real coding started.
Mnemonic "G-Q-B-E-R-E" : "Good Quality Buns Everyone Really Enjoys" = Gather, Quick design, Build, Evaluate, Refine, Engineer.
Common mistake: Delivering the throwaway prototype as the product. It was built fast and is not meant for real use.
Quick recall Prototype = quick sample, customer feedback loop, then build properly. Use when requirements are unclear.

1.9 Evolutionary Models: Incremental and Evolutionary Development

Don't deliver everything at once; deliver a usable core first and grow it release by release. (thoda thoda karke pura)

Definition (Incremental model): The incremental model delivers software in a series of increments; each increment passes through analysis, design, coding and testing, and adds new functionality to the previous release. The first increment is the core product. Aggarwal & Singh call this the iterative enhancement model.
  • Requirements are broadly known and prioritised; most important features go in increment 1 (core product).
  • Each increment is a mini waterfall; customer uses each release and feedback shapes the next. (har release pe kaam aane layak software)
  • Advantages: working software early; lower initial cost; easier testing of small increments; risk spread over releases; customer feedback on each release.
  • Disadvantages: needs good planning and design so increments fit together; total cost may be higher; clear module boundaries needed up front.
  • When to use: requirements clear but full delivery takes long; market needs early release; limited staff at the start.
  • RAD (Rapid Application Development) is a high-speed incremental model using component reuse and parallel teams for a 60-90 day cycle; some books list it here.
Definition (Evolutionary development model): In evolutionary development an initial version is built from an outline description, exposed to user comments, and refined through many versions until an adequate system is developed; specification, development and validation happen concurrently.
  • Two kinds: exploratory development (start with well-understood parts, add features the customer proposes) and throwaway prototyping (understand requirements).
  • Advantages: handles unclear and changing requirements; users see progress early; system matches real needs.
  • Disadvantages: process not visible (few documents); continual change can corrupt structure; hard to estimate cost and time.
  • When to use: small/medium interactive systems with unclear requirements; research-type projects.
BasisIncremental modelEvolutionary development
RequirementsMostly known at start, divided into incrementsNot fully known; discovered through versions
Each cycle deliversA new set of planned featuresAn improved version of the whole system
PlanningIncrements planned in advanceNext version decided by user feedback
DocumentationDocumented per incrementOften weak; low visibility
Example
Incremental: a food-delivery app ships Release 1 = menu + order; Release 2 = live tracking; Release 3 = ratings and coupons.
Evolutionary: a new campus "lost and found" portal starts as a rough version and changes shape after every round of student feedback.
Incremental adds planned pieces; evolutionary reshapes the whole system.
Mnemonic Incremental = Add (new room each release); Evolutionary = Grow (same plant keeps changing shape).
Common mistake: Treating incremental and evolutionary as identical. Incremental needs requirements up front; evolutionary discovers them.
Quick recall Incremental: core first, planned releases, each a mini waterfall. Evolutionary: outline → versions refined by user feedback.

1.10 Spiral Model

Go round in loops; in every loop, first find the biggest risk and kill it, then build a little more. (har chakkar mein pehle khatra dekho)

Definition: The spiral model, proposed by Barry Boehm, is a risk-driven evolutionary model that combines the iterative nature of prototyping with the systematic aspects of the waterfall model. Development proceeds in loops of a spiral; each loop passes through four quadrants.
  • Quadrant 1 – Determine objectives, alternatives and constraints: what this loop must achieve (performance, functionality), alternative ways (buy, reuse, build), and constraints (cost, schedule).
  • Quadrant 2 – Evaluate alternatives, identify and resolve risks: risk analysis; uncertain areas are tested with prototypes, simulations, benchmarks. This quadrant makes the model special. (khatra pehchaano aur hatao)
  • Quadrant 3 – Develop and verify next-level product: design, code, test the product for this loop (can follow waterfall-style steps).
  • Quadrant 4 – Plan next iteration: customer reviews the results; plans made for the next loop; decide whether to continue.
  • Radius of the spiral = cumulative cost so far; angular movement = progress in the current loop.
  • Meta-model: the spiral model contains the other models. One loop with little risk analysis looks like waterfall; using prototypes in quadrant 2 gives prototyping; repeated loops give evolutionary development. Hence Aggarwal & Singh call it a meta model.
  • Number of loops is not fixed; it depends on the risks of the project.
AdvantagesDisadvantages
Explicit risk analysis in every loop; risks reduced earlyNeeds experts in risk assessment; success depends on them
Suits large, complex, high-risk projectsCostly; not worth it for small or low-risk projects
Changes and new requirements can enter in later loopsComplex to manage; end of project not easy to predict
Customer reviews each loop; prototypes give early feedbackNeeds more documentation and review meetings per loop

When to use: large and expensive projects; high-risk or new technology; requirements complex or evolving; e.g. a new satellite ground-control system or a national-scale banking platform.

Mnemonic Quadrants "O-R-D-P" : "Only Risky Designs Pay" = Objectives, Risk analysis, Develop, Plan. Clockwise from top-left.
Common mistake: Forgetting the risk analysis quadrant, or labelling the spiral anticlockwise with random order. The order is Objectives → Risk → Develop → Plan.
Quick recall Spiral (Boehm) = risk-driven loops of 4 quadrants: objectives, risk analysis, develop & verify, plan next. A meta-model.

No model is best for every project; pick the one that fits how clear the requirements are and how risky the project is. (project dekh ke model chuno)

Definition: Selection of a life cycle model is the decision of which process model to follow, based on requirement clarity, project size, risk, customer involvement and delivery needs.

1.12 Short answers (1 mark)

Define software engineering (IEEE).
The application of a systematic, disciplined, quantifiable approach to the development, operation and maintenance of software, that is, the application of engineering to software.
What is software? Give its formula.
Software is a set of programs with their documentation and operating procedures. Software = Programs + Documentation + Operating procedures.
Differentiate program and software.
A program is small code written by one person for personal use with little documentation. Software is large, built by a team for many users, with full documentation and a user interface.
"Software does not wear out." Explain.
Software has no physical parts, so it does not suffer wear like hardware (bathtub curve). It deteriorates because changes introduce new defects, shown as spikes on the actual failure curve.
What is software crisis?
The problems of software development: projects over budget, late, poor in quality, unmaintainable and not meeting requirements. Software engineering emerged as its solution.
List two causes of software crisis.
Growing size and complexity of software, and the absence of a systematic process (ad-hoc code-and-fix development, poor estimation and requirements).
Define software process.
A set of activities, actions and tasks, with associated results, carried out to develop and maintain software. Generic activities: communication, planning, modeling, construction, deployment.
What are umbrella activities?
Activities applied throughout the process: project tracking and control, risk management, SQA, technical reviews, measurement, configuration management, reusability management, work product preparation.
List any four characteristics of a good software process.
Understandability, visibility, reliability, rapidity (others: supportability, acceptability, robustness, maintainability).
What is SDLC?
The software development life cycle is the period from conception of software to its retirement, passing through feasibility, requirements, design, coding, testing and maintenance.
Differentiate classical and iterative waterfall.
Classical waterfall is strictly sequential with no going back. Iterative waterfall adds feedback paths so errors found in a later phase can be corrected in the earlier phase where they occurred.
What is a prototype?
A quick, partial, low-cost working version of a system with limited functionality, built to understand and confirm customer requirements.
Throwaway vs evolutionary prototyping.
A throwaway prototype is discarded after requirements are clarified. An evolutionary prototype is refined step by step into the final system.
What is an increment?
A deliverable part of the software that adds new functionality to earlier releases; the first increment is the core product.
Name the four quadrants of the spiral model.
(1) Determine objectives, alternatives, constraints; (2) evaluate alternatives, identify and resolve risks; (3) develop and verify next-level product; (4) plan next iteration.
Why is the spiral model called a meta-model?
Because it includes other models: a single low-risk loop behaves like waterfall, prototyping is used in risk analysis, and repeated loops give evolutionary development.

How we find out WHAT the customer wants, model it (DFD, data dictionary, ER) and write it down as an SRS. One running example throughout: a Student Result Management System (SRMS).

2.1 Requirements and their types

A requirement is one thing the software must do, or one condition it must satisfy. (software se kya chahiye, uski list)

Definition: A requirement is a feature of the system or a description of something the system is capable of doing in order to fulfil the system's purpose. IEEE 610.12 defines it as a condition or capability needed by a user to solve a problem or achieve an objective.
  • Functional requirements: what the system must DO: inputs, processing, outputs. SRMS example: "The system shall compute the total and grade of each student." (kaam kya karega)
  • Non-functional requirements: HOW WELL it does it: performance, reliability, security, usability, portability. SRMS: "Result of 2,000 students shall be computed within 10 seconds." (kitna achha karega)
  • Domain requirements: come from the application area, not from any one user. SRMS: "A student scoring below the university pass mark in a subject is declared FAIL in that subject."
  • Non-functional sub-types (Sommerville): product (speed, reliability), organisational (standards, process), external (legal, ethical, interoperability).
  • Stakeholder: anyone who is affected by or has a say in the system: customer, end users, developers, testers, managers. SRMS stakeholders: students, teachers, exam cell, college management.

MeaningWhat the system doesHow well the system does it (quality)

Mnemonic K-U-U: Known = said, Unknown = forgot, Undreamt = never imagined.
Common mistake: "The system shall be secure" is NOT a functional requirement just because it says "shall". Security is a quality, so it is non-functional.
Quick recall Functional = what, Non-functional = how well, Domain = from the field. Known / Unknown / Undreamt.

2.2 Requirement engineering process

Requirement engineering is the disciplined way of turning a customer's vague idea into a signed, checked document. (idea se SRS tak ka safar)

Definition: Requirement engineering is the systematic use of proven principles, techniques and tools to elicit, analyse, document, review and manage the requirements of a software system. Its output is the Software Requirements Specification (SRS).
  • Requirements elicitation: gathering requirements from stakeholders by interviews, brainstorming, FAST, QFD, use cases. (nikalwana / collect karna)
  • Requirements analysis: studying the gathered requirements, removing conflicts and gaps, and modelling them (context diagram, DFD, data dictionary, ER diagram, prototype).
  • Requirements documentation: writing the final requirements in a standard form: the SRS.
  • Requirements review (validation): customer and developers check the SRS for correctness, completeness and consistency before it is signed. (sahi likha hai ya nahi)
  • Requirements management: controlling changes to requirements during the project, keeping them traceable to design, code and tests.
  • Why it matters: an error in requirements found late costs far more to fix than the same error found early, so effort spent here saves rework.
Common mistake: Some books (Sommerville) list "feasibility study, elicitation and analysis, specification, validation". Same idea, different names; write the Aggarwal & Singh four steps plus management for this syllabus.
Mnemonic "Every Artist Draws, Reviews, Manages" = Elicitation, Analysis, Documentation, Review, Management.
Quick recall Elicit, Analyse, Document, Review (+ Manage) → SRS.

2.3 Requirement elicitation: interviews and brainstorming

Elicitation means drawing requirements out of people's heads. (logon se pooch-pooch ke requirements nikalna)

Definition: Requirement elicitation is the activity of discovering the requirements of a system by communicating with customers, users and other stakeholders. It is also called requirements gathering or requirements capture.

Interviews

  • Most common technique; analyst talks to stakeholders one-to-one or in small groups.
  • Unstructured (open-ended) interview: no pre-set agenda; free discussion to understand the problem. Good at the start. (khuli baat-cheet)
  • Structured interview: a prepared agenda of fairly open questions; every interviewee answers the same set. Good for comparing views.
  • Groups to interview (Aggarwal & Singh): entry-level personnel, middle-level stakeholders, managers, and the users of the software (most important, they use it daily).
  • Limitations: interviewee may not know what to ask for; takes time; answers depend on the interviewer's skill.

Brainstorming

  • Brainstorming: a group technique to generate many new ideas quickly and share them freely.
  • A facilitator leads, handles group bias and conflicts; one person records every idea where all can see it.
  • Rule: no criticism during the session; even wild ideas are written down. (koi idea galat nahi)
  • Output: a list of ideas, which is then reviewed and prioritised; duplicate or impossible ideas are removed.

Comparison of answersEasyDifficult
RiskMay miss unexpected pointsMay drift off topic
Example (SRMS)
Interview teacher: "How do you submit internal marks today?" → requirement: bulk upload of marks.
Brainstorm with exam cell: "SMS result alert", "re-evaluation request", "rank list" → prioritised later.

2.4 FAST (Facilitated Application Specification Technique)

FAST is a well-run joint meeting where customers and developers build the requirement list together. (dono team ek table pe)

Definition: FAST (Facilitated Application Specification Technique) is a team-oriented elicitation approach in which customers and developers work together in a facilitated meeting to identify the problem, propose elements of the solution, negotiate different approaches and specify a preliminary set of requirements.

Guidelines

  • Meeting held at a neutral site; attended by both developers and customers.
  • Rules for preparation and participation are fixed in advance.
  • An agenda is formal enough to cover all important points, informal enough to allow free flow of ideas.
  • A facilitator (customer, developer or an outsider) controls the meeting.
  • A definition mechanism is used: worksheets, flip charts, wall stickers, electronic board or chat room.

The lists every participant brings

ListMeaningSRMS example
ObjectsThings around, produced by, or used by the systemStudent, marks, marksheet, subject
ServicesProcesses / functions acting on objectsRegister student, enter marks, compute result
ConstraintsCost, size, business rulesPass mark rule, runs on college server
Performance criteriaSpeed, accuracyResult of a class in under 10 s, zero calculation error
  • Mini-specification: a short elaboration of one list entry (an object or service) written by a sub-team, then presented to all for additions and deletions.
  • Unresolved points go to an issues list; each attendee also writes validation criteria; one sub-team writes the complete draft specification.
  • Advantage: shared ownership, fewer misunderstandings. Limitation: needs a skilled facilitator and everyone's time together.

2.5 QFD (Quality Function Deployment)

QFD turns the voice of the customer into technical requirements, ranked by what the customer values most. (customer ki awaaz ko technical bhasha mein)

Definition: Quality Function Deployment (QFD) is a quality management technique that translates the needs of the customer into technical requirements for software, with emphasis on maximising customer satisfaction. It originated in Japanese manufacturing in the 1970s.

Steps of QFD (Aggarwal & Singh)

  1. Identify all stakeholders (customers, users, developers); note initial requirements and constraints.
  2. List requirements from the customer's point of view.
  3. Assign a value of importance to each requirement, e.g. 5 very important, 4 important, 3 nice to have, 2 not important, 1 unrealistic / needs exploration.
  4. Translate high-value customer requirements into technical requirements, and classify the final list: achievable now, deferred (with reason), impossible (dropped).
Example (SRMS importance rating)
Correct grade calculation ........ 5 (expected)
Printable marksheet .............. 5 (normal)
Marks upload by Excel file ........ 4 (normal)
SMS alert when result declared .... 3 (exciting)
Voice-based result enquiry ........ 1 (needs exploration, deferred)
Build the 5s and 4s first; defer or drop the 1s.
Mnemonic "No Extra Excitement": Normal, Expected, Exciting.
Common mistake: Expected requirements are not "less important" because nobody states them. Their absence causes the most dissatisfaction.
Quick recall QFD = customer voice → technical requirements. Normal / Expected / Exciting. Rate importance 1 to 5. House of Quality = WHATs vs HOWs.

2.6 Use case approach and comparison of techniques

A use case tells the story of how a user and the system interact to get one job done. (user system se kya karwata hai, step by step)

Definition: A use case is a structured description of a sequence of interactions between an actor and the system that yields a result of value to that actor. The use case approach (introduced by Ivar Jacobson) captures requirements from the user's point of view.
  • Actor: an external role (person or another system) that interacts with the system; drawn as a stick figure. (role, naam nahi)
  • Use case: one goal the actor achieves; drawn as an ellipse with a verb phrase ("Enter Marks").
  • System boundary: rectangle separating the system from actors.
  • Association: line between actor and use case. Relationships between use cases: <<include>> (always uses another) and <<extend>> (optional extra behaviour).
  • Use case description (template): name, brief description, actors, pre-condition, basic flow of events, alternative flows, post-condition, special requirements.
Example: use case "Enter Marks"
Actor: Teacher. Pre-condition: teacher is logged in.
Basic flow: 1 select subject → 2 system lists roll numbers → 3 teacher types marks → 4 system validates 0 to 100 → 5 marks saved.
Alternative flow: marks out of range → error shown, re-enter.
Post-condition: marks stored for every student of that subject.

2.7 Requirements analysis

Analysis cleans the raw requirement list: removes conflicts, fills gaps and models the system on paper. (kachcha maal ko saaf karna)

Definition: Requirements analysis is the process of studying and refining the elicited requirements to remove inconsistencies, ambiguities and omissions, and representing them with models so that the customer and developer have the same understanding.
  • Draw the context diagram: whole system as one bubble with external entities around it; fixes the system boundary.
  • Develop prototype (optional): a quick working model / screen mock-up so the customer can react to something visible. (demo dikha ke feedback)
  • Model the requirements: graphical models of functions and data: DFD, data dictionary, ER diagram (also state diagrams, decision tables).
  • Finalise the requirements: inconsistencies and ambiguities resolved with the customer; the agreed set goes into the SRS.
  • Typical problems found: conflicting requirements (two users want opposite things), vague words ("fast", "user-friendly"), missing cases (what if a student is absent?).
Quick recall Context diagram → Prototype → Model (DFD, DD, ER) → Finalise.

2.8 Data Flow Diagrams (DFD)

A DFD shows how data enters, moves through, is stored in and leaves a system. It shows data, not control. (data kahan se aaya, kahan gaya)

Definition: A Data Flow Diagram (DFD) is a graphical representation of the flow of data through a system, showing the external entities, processes that transform data, data stores and the data flows between them. It is also called a bubble chart.
SymbolNameMeaningNaming rule
CircleProcessTransforms input data into output dataVerb phrase + number: "3.0 Compute Result"
RectangleExternal entity (source / sink)Person or system outside, sends or receives dataNoun: "Teacher"
Parallel linesData storeData at rest (file, table)Noun + id: "D2 Marks"
ArrowData flowData in motion between componentsNoun: "marks record"

Gane and Sarson notation draws a process as a rounded rectangle; the meaning is the same.

Rules for drawing a DFD

  • Every process must have at least one input and one output (no black hole, no miracle). (kuch aaye bina kuch nahi niklega)
  • Data cannot flow directly entity → entity, entity → store, or store → store; a process must be in between.
  • Every data flow is named (except flows into/out of a store may take the store's name).
  • A DFD shows no control: no loops, no decisions, no sequence. It is not a flowchart.
  • Balancing: inputs and outputs of a parent process must equal the net inputs and outputs of its child diagram.
  • Processes are numbered; child processes of 3.0 are 3.1, 3.2, 3.3 (leveling).

Levels of DFD

  • Level 0 = context diagram: the whole system as ONE process, with all external entities and flows. No data stores.
  • Level 1: the single bubble exploded into main processes (usually 3 to 7), with data stores.
  • Level 2: one level-1 process exploded further. Stop when each process is simple enough to describe in a mini-spec.

2.9 Data dictionary

The data dictionary is the glossary of every data item named in the DFD, written in a precise notation. (DFD ke har naam ka matlab)

Definition: A data dictionary is a repository that contains descriptions of all data objects used or produced by the software, i.e. every data flow, data store and data element in the DFD, together with their composition, aliases and usage.
  • Purpose: gives one precise meaning to every name, so analysts, designers, programmers and testers use the same terms. (sab ek hi bhasha bolein)
  • Removes ambiguity and duplicate names (aliases); helps check DFD consistency and later database design.
  • Typical contents of an entry: name, aliases, where used / how used (input, output, store), content description (in notation), supplementary information (type, range, default).
  • Entries exist for data flows, data stores and elementary data items (the smallest units, e.g. roll_no).
  • Usually maintained with a CASE tool so that it stays consistent with the diagrams.

2.10 Entity-Relationship (ER) diagrams

A DFD models what the system does with data; an ER diagram models what the data itself is and how pieces of data are related. (data ke beech rishte)

Definition: An Entity-Relationship (ER) diagram is a graphical data model, proposed by Peter Chen (1976), that represents the entities of a system, their attributes and the relationships among entities.

Entities and attributes

  • Entity: a real-world object with independent existence about which data is stored (Student, Subject). Entity set = collection of similar entities.
  • Weak entity: cannot be uniquely identified by its own attributes; depends on an owner entity through an identifying relationship (e.g. Dependent of an Employee). Double rectangle.
  • Key attribute: uniquely identifies each entity (Roll_No); underlined.
  • Composite attribute: can be divided into sub-parts (Name = First + Last); sub-ellipses attached to it.
  • Multivalued attribute: can hold many values for one entity (Phone numbers); double ellipse.
  • Derived attribute: computed from another attribute (Age from DOB, Total from marks); dashed ellipse. (store nahi, calculate hota hai)

Relationships

  • Relationship: an association among entities ("Student Takes Subject"); diamond. A relationship may have its own attribute (Marks on Takes).
  • Degree: number of entity sets taking part: unary (1, e.g. Student mentors Student), binary (2, most common), ternary (3).
  • Cardinality: maximum number of entities on one side related to one entity on the other side: 1:1, 1:N, M:N.
  • Participation: total (every entity must participate; double line) or partial (some may not; single line).
  • Reading Fig 2.17: a student takes many subjects and a subject is taken by many students (M:N); Marks belongs to the pair (student, subject), so it is an attribute of the relationship.
  • One teacher teaches many subjects (1:N). The double line shows total participation of SUBJECT: every subject must have a teacher.

2.11 Requirements documentation and nature of SRS

The SRS is the contract between customer and developer: what will be built, written so both sides read it the same way. (dono ke beech likhit agreement)

Definition: A Software Requirements Specification (SRS) is a document that completely describes what the proposed software should do, without describing how it will do it. Requirements documentation is the activity of writing the analysed requirements into this SRS.

Requirements documentation

  • Documentation is the third step of requirement engineering; its output is the SRS, which is then reviewed.
  • Readers of the SRS: customers and users (check it is what they want), developers (design from it), testers (write test cases), managers (estimate cost and schedule), maintainers.
  • Uses of the SRS: basis of agreement, reduces development effort and rework, basis for cost and schedule estimates, baseline for validation and verification, eases enhancement later.

Nature of SRS: what it must address

  • Functionality: what the software is supposed to do. SRMS: compute total and result status.
  • External interfaces: how the software interacts with people, hardware and other software. SRMS: web form for teachers, printer for marksheets.
  • Performance: speed, availability, response time, recovery time. SRMS: 200 teachers online at once.
  • Attributes: portability, correctness, maintainability, security. SRMS: only a teacher can change marks.
  • Design constraints imposed on the implementation: required standards, language, database integrity policy, resource limits, operating environment.

What an SRS should NOT include

  • No design details: module partitioning, algorithms, database table layout. (kya banana hai, kaise nahi)
  • No project requirements: cost, delivery schedule, staffing, reporting procedures, development method, quality assurance plan.
  • No extra constraints beyond what is truly required; it should describe the product, not the project.

2.12 Characteristics of a good SRS

A good SRS is one that every reader interprets the same way and every requirement in it can be checked. (ek hi matlab, har line test ho sake)

Definition: According to IEEE 830, a good SRS should be correct, unambiguous, complete, consistent, ranked for importance and/or stability, verifiable, modifiable and traceable.
  • Correct: every stated requirement is one that the software shall meet; checked against customer needs. Bad: pass mark written as 40 when the university rule says 35 (if the rule is 35).
  • Unambiguous: each requirement has exactly one interpretation. Bad: "result shall be shown quickly". Good: "within 3 seconds".
  • Complete: includes all significant requirements, the response to all valid and invalid inputs, labels for all figures and tables, and definitions of all terms; no "TBD" left.
  • Consistent: no subset of requirements conflicts (e.g. one line says grade scale A to F, another says 10-point CGPA only). (aapas mein takraav nahi)
  • Ranked for importance and/or stability: each requirement tagged essential / conditional / optional, and how likely it is to change.
  • Verifiable: a finite, cost-effective process exists to check the software meets it. "User friendly" is not verifiable.
  • Modifiable: structure (contents, index, cross-references) lets changes be made easily and consistently; each requirement stated only once.
  • Traceable: backward traceability (to its source: a stakeholder, use case) and forward traceability (to design, code, test) via unique ids like FR-3.

2.13 Organization of SRS (IEEE 830 outline)

IEEE 830 gives a standard table of contents so every SRS is arranged the same way. (SRS ka standard dhaancha)

Definition: IEEE Std 830-1998 (Recommended Practice for Software Requirements Specifications) organises an SRS into three main sections: Introduction, Overall description and Specific requirements, followed by appendices and an index.

1 Introduction

  • Purpose: why this SRS exists and who its intended readers are.
  • Scope: name of the product, what it will and will not do, benefits and goals. SRMS: "computes and publishes semester results; does not handle fee payment".
  • Definitions, acronyms, abbreviations: SRMS, CGPA, DFD.
  • References: documents referred to (university ordinance, IEEE 830).
  • Overview: what the rest of the SRS contains and how it is organised.

2 Overall description (background, not detailed requirements)

  • Product perspective: relation to other systems; system, user, hardware, software and communication interfaces; memory constraints; operations; site adaptation.
  • Product functions: summary of major functions (register, enter marks, compute, report).
  • User characteristics: education, experience, technical skill of users (teachers with basic computer skills).
  • Constraints: regulatory policies, hardware limits, interfaces to other applications, security, reliability needs.
  • Assumptions and dependencies: factors that, if changed, change the requirements (college server available during result week).
  • IEEE 830-1998 also has 2.6 Apportioning of requirements: requirements delayed to future versions.

3 Specific requirements (the main body, detailed enough to design and test)

  • External interfaces: every input and output: name, purpose, source/destination, range, format.
  • Functions: fundamental actions on inputs to produce outputs (validity checks, sequence, error handling). Often written as FR-1, FR-2 ...
  • Performance requirements: static (number of users, terminals, data size) and dynamic (transactions per second, response time).
  • Logical database requirements: types of data, access frequency, integrity constraints, retention.
  • Design constraints: standards compliance (report format, audit trail), hardware limitations.
  • Software system attributes: reliability, availability, security, maintainability, portability.
  • The specific requirements can be organised by mode, user class, objects, feature, stimulus or functional hierarchy.
Mnemonic Section 1 "PSDRO" = Purpose, Scope, Definitions, References, Overview. Section 2 "PFUCA" = Perspective, Functions, Users, Constraints, Assumptions. Section 3 "EF-PLDS" = External interfaces, Functions, Performance, Logical database, Design constraints, System attributes.
Common mistake: Writing detailed requirements in section 2. Section 2 only gives background and a summary; every testable detail goes in section 3. (IEEE 830-1998 has since been superseded by ISO/IEC/IEEE 29148, but syllabi and textbooks still teach the 830 outline.)
Quick recall 1 Introduction (PSDRO) → 2 Overall description (PFUCA) → 3 Specific requirements (EF-PLDS) → Appendices, Index.

2.14 Short answers (1 mark)

Define requirement engineering.
Systematic use of principles, techniques and tools to elicit, analyse, document, review and manage software requirements. Its output is the SRS.
Differentiate functional and non-functional requirements.
Functional: what the system does (e.g. compute result). Non-functional: how well it does it: performance, security, usability (e.g. result in 3 seconds).
What are known, unknown and undreamt requirements?
Known: stated by the stakeholder. Unknown: forgotten because not needed now or needed by another stakeholder. Undreamt: stakeholder cannot imagine them due to limited domain knowledge.
Who is a stakeholder?
Any person or group affected by or having influence on the system: customer, users, developers, testers, managers.
Expand FAST and QFD.
FAST: Facilitated Application Specification Technique. QFD: Quality Function Deployment.
List the lists prepared in a FAST meeting.
Objects (around, produced, used by the system), services, constraints, and performance criteria. Sub-teams then write mini-specifications.
What are normal, expected and exciting requirements?
Normal: explicitly stated. Expected: implicit, so basic that customers do not state them. Exciting: beyond customer expectations, delight when present (QFD).
What is a use case? Name its diagram symbols.
Sequence of actor-system interactions giving a result of value. Actor = stick figure, use case = ellipse, system boundary = rectangle, association = line.
Draw / name the symbols of a DFD.
Process = circle, external entity = rectangle, data store = two parallel lines (open box), data flow = named arrow.
What is a context diagram?
Level 0 DFD showing the entire system as a single process with all external entities and data flows; it defines the system boundary.
What is balancing in DFD?
The data flows entering and leaving a parent process must match the net inputs and outputs of its child (lower level) diagram.
Define data dictionary.
A repository of definitions of all data flows, data stores and data items of the DFD, with composition, aliases and usage, written in notation such as =, +, [ | ], { }, ( ).
What does { } and ( ) mean in a data dictionary?
{ } = iteration (repeated), ( ) = optional. Example: marksheet = roll_no + {subject_code + marks}; name = first + (middle) + last.
Define cardinality in ER diagram.
Maximum number of entity instances on one side that can be related to one instance on the other side: 1:1, 1:N or M:N.
What is a weak entity?
An entity that cannot be uniquely identified by its own attributes and depends on an owner entity via an identifying relationship. Drawn as a double rectangle.
What is an SRS?
Software Requirements Specification: document describing completely WHAT the software will do, not HOW; the agreement between customer and developer.
List characteristics of a good SRS.
Correct, unambiguous, complete, consistent, ranked for importance/stability, verifiable, modifiable, traceable (IEEE 830).
Name the three main sections of an IEEE 830 SRS.
1 Introduction, 2 Overall description, 3 Specific requirements (plus appendices and index).
